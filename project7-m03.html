Boîte à outils numérique : NumPy, pandas, polars, Dask, frameworks

Ces bibliothèques ne sont pas interchangeables : chacune répond à une contrainte précise de volume, de latence ou de type de calcul. Ce module explique ce qu'elles font réellement sous le capot, parce que c'est ce qui permet de choisir la bonne — et d'écrire du code dix à cent fois plus rapide sans rien changer d'algorithmique.

1. NumPy : le socle

Tout le reste repose dessus. Un ndarray, c'est un bloc de mémoire contigu et homogène plus une description de la façon de le lire : une forme (shape), un type (dtype) et des pas (strides, le nombre d'octets à sauter pour avancer d'un cran sur chaque axe). Cette séparation entre données et interprétation explique presque tous les comportements de NumPy.

Python
import numpy as np

a = np.arange(12, dtype=np.float64).reshape(3, 4)
a.shape        # (3, 4)
a.strides      # (32, 8) : 32 octets pour changer de ligne, 8 pour changer de colonne
a.nbytes       # 96

b = a.T        # transposée : AUCUNE donnée copiée, seuls les strides sont inversés
b.strides      # (8, 32)
b.base is a    # True → b est une vue sur a

Vues et copies : la source d'erreurs n° 1

Le découpage (slicing) renvoie une vue : modifier la vue modifie l'original. L'indexation « fantaisiste » (par tableau d'indices ou par masque booléen) renvoie une copie.

Python
x = np.arange(10)

v = x[2:5]          # vue
v[0] = 999
x[2]                # 999  → x a été modifié

c = x[[2, 3, 4]]    # copie (fancy indexing)
c[0] = -1
x[2]                # 999  → x est intact

# vérifier en cas de doute
np.shares_memory(x, v)   # True
np.shares_memory(x, c)   # False

Broadcasting

Le broadcasting permet d'opérer sur des tableaux de formes différentes sans les dupliquer en mémoire. Les formes sont alignées par la droite ; deux dimensions sont compatibles si elles sont égales ou si l'une vaut 1, auquel cas elle est « étirée » virtuellement (stride mis à 0, donc aucune allocation).

Python
X = np.random.randn(1000, 50)      # (1000, 50)
mu = X.mean(axis=0)                # (50,)      → alignée sur les colonnes
Xc = X - mu                        # (1000, 50) : broadcasting, pas de duplication de mu

# matrice de distances deux à deux, sans boucle ni copie explicite
d = np.linalg.norm(X[:, None, :] - X[None, :, :], axis=-1)   # (1000, 1000)
Attention à la mémoire du broadcasting. La dernière ligne crée un tableau intermédiaire de forme (1000, 1000, 50), soit 400 Mo en float64. Avec 20 000 points au lieu de 1 000, c'est 160 To : le calcul échoue. Pour ce cas précis, scipy.spatial.distance.cdist ou sklearn.metrics.pairwise_distances font le travail par blocs. Règle : quand une expression vectorisée crée un axe supplémentaire, calculer sa taille avant de l'exécuter.

Vectoriser, vraiment

Une boucle Python sur un tableau NumPy paie l'interpréteur à chaque itération. L'opération vectorisée équivalente descend dans une boucle C compilée, souvent parallélisée et vectorisée SIMD.

Python
x = np.random.randn(1_000_000)

# ≈ 400 ms — l'interpréteur gère un million d'itérations
out = np.array([v ** 2 + 3 * v if v > 0 else 0.0 for v in x])

# ≈ 4 ms — une seule descente dans le code natif
out = np.where(x > 0, x ** 2 + 3 * x, 0.0)

Deux compléments utiles : np.einsum exprime produits et contractions de tenseurs de façon compacte et souvent plus efficace qu'une suite de reshape / matmul ; et Numba (@njit) compile à la volée une boucle Python en code machine, ce qui reste la meilleure option pour les algorithmes séquentiels non vectorisables (une récurrence, un automate).

Types : choisir, pas subir

Le dtype par défaut est float64. Passer en float32 divise la mémoire par deux et accélère souvent les calculs — c'est d'ailleurs le type natif de la plupart des GPU. Attention toutefois : en float32, la somme de plusieurs millions de termes accumule une erreur d'arrondi notable (utiliser dtype=np.float64 dans np.sum si la précision compte). Pour les entiers, un int8 silencieusement débordé donne des résultats faux sans aucun avertissement.

2. pandas : forces et pièges

pandas ajoute à NumPy ce qui manque pour des données réelles : des colonnes hétérogènes, un index, des étiquettes, et la gestion des valeurs manquantes. C'est l'outil le plus répandu, avec une ergonomie datée et quelques chausse-trappes bien connues.

Python
import pandas as pd

df = (
    pd.read_parquet("data/commandes.parquet")
      .assign(
          date=lambda d: pd.to_datetime(d["date"]),
          marge=lambda d: d["prix"] - d["cout"],
      )
      .query("marge > 0")
      .astype({"categorie": "category"})        # mémoire divisée par 10 sur du texte répété
)

# split-apply-combine
stats = (
    df.groupby(["categorie", pd.Grouper(key="date", freq="ME")])
      .agg(ca=("prix", "sum"), n=("prix", "size"), marge_moy=("marge", "mean"))
      .reset_index()
)

L'écriture chaînée n'est pas qu'une question de style : chaque étape produit un nouvel objet, ce qui évite les mutations en place et donc les états intermédiaires impossibles à reproduire dans un notebook.

Les trois pièges classiques.
1. SettingWithCopyWarning — df[df.a > 0]["b"] = 1 écrit dans un objet temporaire, pas dans df. La forme correcte est df.loc[df.a > 0, "b"] = 1.
2. apply ligne par ligne — df.apply(f, axis=1) repasse par l'interpréteur pour chaque ligne : cent fois plus lent qu'une expression vectorisée équivalente.
3. La mémoire — un DataFrame occupe typiquement 3 à 10 fois la taille du CSV d'origine. Les colonnes textuelles répétées passent en category, les entiers en int32, et df.info(memory_usage="deep") donne le vrai coût.

3. polars : expressions et évaluation paresseuse

polars est écrit en Rust sur le format mémoire Apache Arrow. Deux différences de fond avec pandas : il est multi-thread par défaut (pas de GIL dans le moteur, cf. module 1), et il propose un mode paresseux où la requête est d'abord construite, puis optimisée, puis exécutée — comme un moteur SQL.

Python
import polars as pl

q = (
    pl.scan_parquet("data/commandes_*.parquet")       # scan_ = paresseux, rien n'est lu
      .filter(pl.col("date") >= pl.date(2025, 1, 1))
      .with_columns(marge=pl.col("prix") - pl.col("cout"))
      .group_by("categorie")
      .agg(
          ca=pl.col("prix").sum(),
          marge_moy=pl.col("marge").mean(),
          n=pl.len(),
      )
      .sort("ca", descending=True)
)

print(q.explain())      # le plan optimisé, comme un EXPLAIN SQL
df = q.collect()        # exécution effective

L'optimiseur fait deux choses décisives : la projection pushdown (seules les colonnes réellement utilisées sont lues sur le disque) et la predicate pushdown (les filtres descendent au plus près de la lecture, parfois jusqu'au niveau des fichiers Parquet, dont les métadonnées permettent de sauter des blocs entiers). Sur un jeu de 50 colonnes dont on n'en utilise que 4, le gain est d'un ordre de grandeur avant même le moindre calcul.

En pratique : facteur 5 à 20 sur les agrégations et jointures par rapport à pandas, et surtout un modèle mental plus propre — le concept d'expression (pl.col("x").sum()) est un objet réutilisable et composable, contrairement aux chaînes de caractères magiques de pandas. Le coût de migration est réel (API différente, index absent) mais les deux cohabitent : df.to_pandas() et pl.from_pandas() sont peu coûteux grâce à Arrow.

4. Dask, Spark, Ray : passer à l'échelle

Dask découpe un grand DataFrame en partitions (des DataFrames pandas), construit un graphe de tâches, puis l'exécute en parallèle — sur plusieurs cœurs ou plusieurs machines, en traitant les partitions au fur et à mesure (out-of-core) plutôt qu'en chargeant tout en mémoire.

Python
import dask.dataframe as dd

ddf = dd.read_parquet("s3://bucket/annee=2025/*.parquet")   # graphe, rien n'est chargé
resultat = (
    ddf[ddf.montant > 0]
       .groupby("client_id")
       .montant.sum()
)
out = resultat.compute()      # déclenche le calcul, renvoie une Series pandas

Le point délicat est le shuffle : toute opération qui redistribue les données entre partitions (groupby sur une clé non triée, jointure sur une colonne quelconque, sort_values) impose de tout faire transiter par le réseau ou le disque. C'est là que passe l'essentiel du temps, et la raison pour laquelle un pipeline distribué mal conçu est plus lent qu'un pipeline local.

  • Dask — même API que pandas/NumPy, idéal pour passer d'un poste de travail à un cluster sans réécrire ;
  • Spark (PySpark) — l'écosystème d'entreprise, très mature, adapté aux vrais téraoctets, avec un coût opérationnel élevé ;
  • Ray — orienté calcul distribué générique (entraînement, tuning, RL, servage) plutôt que DataFrames.

5. Quel outil pour quelle taille de données

arbre de décision
Volume            Outil recommandé                    Remarque
──────────────────────────────────────────────────────────────────────────────
< 1 Go            pandas ou polars                    tout tient en RAM, choisir par goût
1 – 50 Go         polars (lazy) ou DuckDB             la RAM d'une machine moderne suffit
                                                       encore : ne pas distribuer trop tôt
50 – 500 Go       polars streaming, DuckDB, Dask      une grosse machine coûte souvent moins
                                                       cher qu'un cluster mal exploité
> 500 Go          Spark, Dask sur cluster             la complexité devient justifiée
Tableaux denses   NumPy (+ Numba)                     calcul numérique pur
GPU               PyTorch, CuPy, cuDF                 si le calcul est massivement parallèle

Le conseil qui fait gagner le plus de temps

La plupart des jeux de données présentés comme « trop gros » tiennent en mémoire une fois convertis en Parquet, les colonnes inutiles supprimées et les types réduits. Avant de monter un cluster : convertir le CSV en Parquet (compression 5 à 10×, lecture par colonnes), garder les colonnes utiles, échantillonner pour l'exploration. Un cluster mal utilisé est plus lent, plus cher et beaucoup plus difficile à déboguer qu'un ordinateur portable bien utilisé.

6. scikit-learn : l'API qui structure tout

La vraie valeur de scikit-learn n'est pas sa collection d'algorithmes, c'est la régularité de son interface. Trois verbes, et tout objet de l'écosystème s'y conforme :

  • fit(X, y) — apprend des paramètres et les stocke dans l'objet (attributs suffixés par un tiret bas : mean_, coef_) ;
  • transform(X) — applique la transformation apprise ;
  • predict(X) / predict_proba(X) — produit la prédiction.

La conséquence pratique est majeure : un Pipeline qui enchaîne des étapes se comporte lui-même comme un estimateur, donc la validation croisée réajuste toute la chaîne à chaque pli. C'est la protection la plus efficace contre la fuite de données (module 6) : un StandardScaler ajusté hors du pipeline apprendrait la moyenne du jeu de validation.

Python
from sklearn.compose import ColumnTransformer
from sklearn.ensemble import HistGradientBoostingRegressor
from sklearn.impute import SimpleImputer
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import Pipeline, make_pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

num = ["surface", "n_pieces", "age"]
cat = ["ville", "type_bien"]

pre = ColumnTransformer([
    ("num", make_pipeline(SimpleImputer(strategy="median"), StandardScaler()), num),
    ("cat", OneHotEncoder(handle_unknown="ignore", min_frequency=20), cat),
])

modele = Pipeline([
    ("pre", pre),
    ("gbm", HistGradientBoostingRegressor(max_iter=400, learning_rate=0.05)),
])

# tout le prétraitement est réappris à chaque pli : aucune fuite possible
scores = cross_val_score(modele, X, y, cv=5, scoring="neg_root_mean_squared_error")
print(f"RMSE = {-scores.mean():.3f} ± {scores.std():.3f}")

Pour une transformation maison, il suffit d'hériter de BaseEstimator et TransformerMixin pour qu'elle s'intègre partout (pipelines, recherche d'hyperparamètres, sérialisation) :

Python
from sklearn.base import BaseEstimator, TransformerMixin

class ClipOutliers(BaseEstimator, TransformerMixin):
    """Écrête aux quantiles appris sur le train uniquement."""
    def __init__(self, q=0.01):
        self.q = q                       # les hyperparamètres sont des attributs simples

    def fit(self, X, y=None):
        self.lo_ = np.quantile(X, self.q, axis=0)
        self.hi_ = np.quantile(X, 1 - self.q, axis=0)
        return self                       # fit renvoie toujours self

    def transform(self, X):
        return np.clip(X, self.lo_, self.hi_)

7. PyTorch, TensorFlow, BoTorch

Un framework de deep learning apporte trois choses : des tenseurs qui vivent sur GPU, la différentiation automatique, et une bibliothèque de couches et d'optimiseurs. La différentiation automatique est le cœur : pendant le calcul, le framework enregistre le graphe des opérations, puis le remonte en appliquant la règle de dérivation composée pour obtenir les gradients — sans que l'on ait à dériver quoi que ce soit à la main (module 4).

Python — PyTorch
import torch

x = torch.randn(64, 10, device="cuda")
w = torch.randn(10, 1, device="cuda", requires_grad=True)
b = torch.zeros(1, device="cuda", requires_grad=True)

y_pred = x @ w + b
perte = ((y_pred - y) ** 2).mean()

perte.backward()          # remonte le graphe : remplit w.grad et b.grad
print(w.grad.shape)       # (10, 1)

with torch.no_grad():     # mise à jour manuelle : pas de graphe à construire ici
    w -= 0.01 * w.grad
    w.grad.zero_()        # les gradients s'ACCUMULENT : oublier ce reset est un bug classique
PyTorch vs TensorFlow en 2026
                    PyTorch                      TensorFlow / Keras
Style               impératif ("eager")          graphe, ou Keras de haut niveau
Débogage            pdb, print : du Python       plus indirect
Recherche           domine très largement        minoritaire
Production          TorchServe, vLLM, ONNX       TF Serving, TFLite, écosystème mobile mûr
Compilation         torch.compile                XLA / jit_compile
À apprendre         oui, par défaut              si l'existant de l'équipe l'impose

Pour un apprentissage aujourd'hui, PyTorch est le choix par défaut : c'est la langue de la recherche, donc celle dans laquelle les nouveautés arrivent en premier. torch.compile réconcilie confort et performance en compilant le graphe à la volée. JAX est un troisième acteur, élégant (fonctions pures, grad, vmap, jit) et très utilisé en recherche scientifique.

BoTorch est une bibliothèque construite sur PyTorch pour l'optimisation bayésienne : modèles de substitution par processus gaussiens, fonctions d'acquisition différentiables, optimisation multi-objectif. Son intérêt pour un profil ingénieur est direct — optimiser un système dont chaque évaluation coûte cher (une simulation, un essai physique). C'est l'objet du module 9.

Ce qu'il faut retenir du module

  • NumPy : vue contre copie, broadcasting (en surveillant la taille des intermédiaires), vectorisation plutôt que boucle, dtypes choisis.
  • pandas pour l'ergonomie et l'écosystème ; polars pour la vitesse, le multi-threading et l'optimisation de requêtes.
  • Ne pas distribuer trop tôt : Parquet, colonnes utiles et types réduits règlent la majorité des problèmes de volume.
  • scikit-learn : tout passer par des Pipeline, c'est la meilleure assurance contre la fuite de données.
  • PyTorch comme framework par défaut ; les gradients s'accumulent, il faut les remettre à zéro.

What this module covers

  • Dask, Spark and Ray: partitions, task graphs, and why shuffles dominate distributed runtimes.
  • A decision table for picking a tool by data size — and why most "too big" datasets are not.
  • scikit-learn: the estimator API, pipelines and ColumnTransformer as leakage protection, writing a custom transformer.
  • PyTorch vs TensorFlow, automatic differentiation in practice, and a first look at BoTorch.
