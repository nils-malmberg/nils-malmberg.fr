Fondations Python, outillage et concurrence

Ce module ne réapprend pas Python : il installe l'environnement de travail d'un projet de data science et traite les points qui font perdre du temps quand on vient du calcul scientifique — la gestion des dépendances, la structure d'un projet, et surtout le modèle d'exécution concurrent de Python, qui n'a rien d'évident.

1. Structure d'un projet Python

Un notebook exploratoire est un brouillon, pas un livrable. Dès qu'un bout de code est appelé deux fois, il migre dans un module importable. La disposition standard aujourd'hui est le src layout :

arborescence
mon-projet/
├── pyproject.toml        # métadonnées + dépendances + config des outils
├── uv.lock               # versions exactes, versionné dans Git
├── README.md
├── src/
│   └── mon_projet/
│       ├── __init__.py
│       ├── data.py       # chargement / nettoyage
│       ├── features.py   # transformations
│       └── models.py     # entraînement / inférence
├── notebooks/            # exploration, jamais de logique réutilisable
├── tests/
└── data/                 # ignoré par Git (voir section 6)

L'intérêt du src/ : le paquet n'est pas importable depuis la racine par accident. Si les tests passent, c'est que le paquet est réellement installé dans l'environnement, donc que ce qui est testé est ce qui sera distribué. Le pyproject.toml centralise tout — métadonnées, dépendances et configuration des outils :

pyproject.toml
[project]
name = "mon-projet"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "numpy>=2.0",
    "polars>=1.0",
    "scikit-learn>=1.5",
]

[dependency-groups]
dev = ["pytest>=8", "ruff>=0.6", "mypy>=1.11"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]
line-length = 100

[tool.pytest.ini_options]
testpaths = ["tests"]

Notebooks : la règle que je m'impose

Un notebook sert à regarder les données et à essayer des choses. Tout ce qui doit être reproductible (chargement, features, entraînement) vit dans src/ et est importé dans le notebook. Sinon on se retrouve avec une logique métier qui n'existe que dans un état d'exécution perdu, dépendant de l'ordre dans lequel les cellules ont été lancées.

2. UV : environnements et dépendances

UV (écrit en Rust par Astral, les auteurs de ruff) remplace à lui seul pip, virtualenv, pyenv, pipx et poetry. Deux différences pratiques avec l'existant : il est un à deux ordres de grandeur plus rapide, et il gère aussi l'installation des interpréteurs Python eux-mêmes.

cycle de travail courant
# créer un projet (génère pyproject.toml, .venv, uv.lock)
uv init mon-projet && cd mon-projet

# installer un interpréteur précis, sans toucher au Python système
uv python install 3.12

# ajouter une dépendance : résolution + install + mise à jour du lock
uv add "polars>=1.0" scikit-learn
uv add --dev pytest ruff mypy

# recréer l'environnement exact d'un collègue (ou de la CI)
uv sync

# lancer du code dans l'environnement, sans l'activer
uv run python -m mon_projet.train
uv run pytest

# script autonome avec ses dépendances déclarées dans son en-tête (PEP 723)
uv run --with pandas,matplotlib analyse.py

Résolution, lockfile et reproductibilité

La distinction essentielle : pyproject.toml déclare des contraintes (« numpy au moins 2.0 »), uv.lock enregistre la solution exacte retenue (numpy 2.1.3, avec son hash). Le premier exprime l'intention, le second garantit que deux machines installent exactement les mêmes octets. Les deux se versionnent dans Git ; uv.lock est multiplateforme, contrairement à un requirements.txt figé par pip freeze.

Le piège CUDA. En ML, la dépendance qui casse la reproductibilité n'est pas Python mais le couple pilote GPU / version de CUDA compilée dans les wheels de PyTorch. UV sait pointer un index alternatif ([tool.uv.sources] vers le dépôt cu124 par exemple), mais l'environnement « identique » s'arrête à la frontière du conteneur : c'est une des raisons de passer à Docker dès qu'un GPU entre en jeu (module 2).

Face à conda : conda reste utile quand on dépend de bibliothèques système non-Python compliquées (certains solveurs, GDAL, MKL configuré finement). Pour un projet de ML standard, UV est plus rapide, plus simple, et son lockfile est plus fiable qu'un environment.yml.

3. Le typage qui sert vraiment

Les annotations de type ne sont pas vérifiées à l'exécution : ce sont des métadonnées lues par les outils (mypy, pyright) et par l'éditeur. En data science, leur rendement est maximal aux frontières — signatures de fonctions publiques, structures de configuration, formats d'entrée/sortie — et faible à l'intérieur d'un calcul numérique.

Python
from dataclasses import dataclass
from pathlib import Path
import numpy as np
from numpy.typing import NDArray

@dataclass(frozen=True, slots=True)
class TrainConfig:
    """Configuration d'entraînement : immuable, hashable, auto-documentée."""
    data_path: Path
    n_estimators: int = 300
    learning_rate: float = 0.05
    random_state: int | None = 42

def rmse(y_true: NDArray[np.float64], y_pred: NDArray[np.float64]) -> float:
    return float(np.sqrt(np.mean((y_true - y_pred) ** 2)))

frozen=True interdit la mutation (une config qui change en cours de route est une source de bugs irreproductibles), slots=True réduit l'empreinte mémoire et interdit les attributs fantômes dus à une faute de frappe. Pour valider des données externes (fichier YAML, requête HTTP), on passe à pydantic, qui lui vérifie et convertit à l'exécution — c'est le socle de FastAPI (module 2).

À retenir

Annotez les frontières, pas les boucles internes. Un NDArray[np.float64] ne dit rien de la forme du tableau — la vraie source d'erreurs en ML. D'où l'habitude d'écrire la forme attendue en commentaire ((n_samples, n_features)) et de la vérifier avec un assert X.ndim == 2 en début de fonction.

4. Itérateurs, générateurs et mémoire

La différence entre un script qui traite 50 Go et un script qui meurt en MemoryError tient souvent à une seule habitude : produire les données paresseusement plutôt que de les matérialiser.

Python
from collections.abc import Iterator
import itertools

def lire_lignes(chemin: str) -> Iterator[dict]:
    """Streaming : une ligne en mémoire à la fois, quel que soit le fichier."""
    with open(chemin, encoding="utf-8") as f:
        for ligne in f:                 # le fichier est déjà un itérateur
            yield json.loads(ligne)

def par_lots(it, taille: int):
    """Regroupe un itérable en lots — indispensable pour l'inférence batchée."""
    it = iter(it)
    while lot := list(itertools.islice(it, taille)):
        yield lot

# consommation : mémoire O(taille du lot), pas O(taille du fichier)
for lot in par_lots(lire_lignes("events.jsonl"), 1024):
    scores = model.predict(lot)

Trois réflexes utiles : itertools.islice / chain / groupby plutôt que des boucles à index ; functools.lru_cache sur les fonctions pures coûteuses ; et collections.Counter / defaultdict pour les comptages, systématiquement plus rapides qu'un dict géré à la main. En Python 3.12+, itertools.batched fait le travail de par_lots nativement.

5. Qualité : ruff, pytest, pre-commit

ruff remplace flake8, isort, black et une bonne partie de pylint, en une fraction du temps : uv run ruff check --fix . puis uv run ruff format .. Le formatage automatique n'est pas un détail esthétique : il supprime les diffs de style, qui polluent les revues et masquent les vrais changements.

Tester du code de data science demande d'adapter la cible. On ne teste pas « le modèle a 92 % d'accuracy » (c'est du monitoring, module 12), on teste la plomberie :

tests/test_features.py
import numpy as np
import pytest
from mon_projet.features import ajouter_features_temporelles

def test_pas_de_fuite_temporelle(df_exemple):
    """Une feature calculée à t ne doit jamais utiliser d'information de t+1."""
    out = ajouter_features_temporelles(df_exemple)
    assert out["moyenne_mobile_7j"].iloc[0] != out["cible"].iloc[0]

@pytest.mark.parametrize("n_lignes", [0, 1, 1000])
def test_robustesse_aux_tailles(n_lignes):
    """Les cas dégénérés — DataFrame vide, une seule ligne — cassent souvent."""
    df = generer_df(n_lignes)
    assert len(ajouter_features_temporelles(df)) == n_lignes

def test_deterministe():
    """Même graine, même résultat : sinon rien n'est reproductible."""
    a = entrainer(seed=0).predict(X_test)
    b = entrainer(seed=0).predict(X_test)
    np.testing.assert_allclose(a, b)

Les tests à haut rendement, par ordre : formes et types de sortie, cas dégénérés (vide, une ligne, toutes valeurs manquantes, une seule classe), déterminisme à graine fixée, invariants métier (« une probabilité est dans [0, 1] », « la somme des parts vaut 1 »), et non-régression sur un jeu de données miniature stocké dans le dépôt. pre-commit branche ruff et les tests rapides sur le git commit pour que rien de mal formé n'entre dans l'historique.

6. Git pour un projet data

Le workflow que j'utilise, volontairement minimal : main toujours fonctionnelle, une branche par sujet, une pull request même en solo (elle force une relecture du diff complet, ce qui attrape beaucoup d'erreurs).

bash
git switch -c feat/gradient-boosting     # branche de travail
git add -p                               # relire chaque morceau avant de l'indexer
git commit -m "feat(model): baseline XGBoost, RMSE 0.42 en CV"

git fetch origin
git rebase origin/main                   # historique linéaire AVANT publication
git push -u origin feat/gradient-boosting

Rebase ou merge ? Rebase tant que la branche est privée : l'historique reste linéaire et lisible. Merge dès qu'elle est partagée : réécrire des commits que quelqu'un d'autre a déjà récupérés casse son dépôt. La règle tient en une phrase : ne jamais réécrire un historique déjà publié.

Les messages suivent la convention Conventional Commits (feat:, fix:, refactor:, docs:) : c'est ce qui permet de générer un changelog et, surtout, de retrouver pourquoi une transformation a été ajoutée six mois plus tard.

Git n'est pas fait pour les données. Un CSV de 2 Go committé reste dans l'historique pour toujours, même supprimé ensuite — chaque clone le retéléchargera. Mettez data/, *.csv, *.parquet, *.pkl, models/ et .ipynb_checkpoints/ dans .gitignore dès le premier commit. Pour versionner données et modèles, voir DVC au module 12. Pour les notebooks, nbstripout retire les sorties avant commit — sans lui, chaque exécution produit un diff illisible de plusieurs milliers de lignes.

7. Concurrence : GIL, threads, processus, asyncio

C'est le point où l'intuition issue du C ou du calcul parallèle classique induit en erreur. Trois modèles coexistent en Python, et choisir le mauvais peut ralentir un programme.

7.1 Le GIL, énoncé correctement

Le Global Interpreter Lock est un verrou de l'interpréteur CPython : un seul thread exécute du bytecode Python à un instant donné dans un processus. Conséquence directe : plusieurs threads Python purs ne consomment pas plus d'un cœur au total. Mais l'énoncé complet est plus intéressant, car le GIL est relâché dans deux situations :

  • pendant une attente d'entrée/sortie (lecture disque, requête réseau, appel à une base de données) ;
  • pendant l'exécution de code natif qui le relâche explicitement — et c'est exactement ce que font NumPy, SciPy, scikit-learn, PyTorch ou polars dans leurs boucles de calcul.

Autrement dit : un produit matriciel NumPy dans quatre threads utilise réellement quatre cœurs, alors qu'une boucle Python pure dans quatre threads n'en utilise qu'un. Depuis Python 3.13 existe un mode expérimental free-threaded (PEP 703) sans GIL, mais l'écosystème scientifique n'y est pas encore entièrement porté : en 2026, on raisonne toujours avec le GIL.

7.2 La question à se poser : où le temps passe-t-il ?

Arbre de décision

  1. Le programme attend-il des I/O ? (API, base de données, fichiers, scraping) → asyncio pour des milliers d'attentes concurrentes, ThreadPoolExecutor si la bibliothèque utilisée est bloquante et synchrone.
  2. Calcule-t-il en Python pur ? (boucles, parsing, logique métier) → ProcessPoolExecutor ou joblib : un processus par cœur, chacun avec son propre GIL.
  3. Calcule-t-il dans NumPy / PyTorch / polars ? → c'est déjà parallèle (BLAS multithreadé). N'ajoutez rien avant d'avoir mesuré : la parallélisation naïve par-dessus dégrade presque toujours les performances.

7.3 Threads : pour attendre, pas pour calculer

Python
from concurrent.futures import ThreadPoolExecutor, as_completed
import requests

def telecharger(url: str) -> bytes:
    return requests.get(url, timeout=10).content   # le GIL est relâché pendant l'attente

urls = [f"https://api.exemple.fr/page/{i}" for i in range(200)]

with ThreadPoolExecutor(max_workers=16) as ex:
    futures = {ex.submit(telecharger, u): u for u in urls}
    for fut in as_completed(futures):
        url = futures[fut]
        try:
            contenu = fut.result()
        except Exception as e:                      # une exception n'explose qu'au .result()
            print(f"échec {url}: {e}")

200 requêtes séquentielles à 100 ms font 20 s ; avec 16 threads, environ 1,3 s. Le gain vient du fait que les threads passent leur temps bloqués, GIL relâché. Deux précautions : as_completed plutôt que map pour traiter les résultats dès qu'ils arrivent, et un timeout systématique — sans lui, un serveur muet bloque un worker indéfiniment.

7.4 Processus : pour calculer en Python pur

Python
from concurrent.futures import ProcessPoolExecutor

def simuler(seed: int) -> float:
    """Monte-Carlo en Python pur : CPU-bound, donc inutile de threader."""
    rng = random.Random(seed)
    return sum(rng.random() ** 2 for _ in range(1_000_000)) / 1_000_000

if __name__ == "__main__":                 # OBLIGATOIRE avec la méthode spawn
    with ProcessPoolExecutor(max_workers=8) as ex:
        resultats = list(ex.map(simuler, range(64), chunksize=4))

Trois contraintes structurelles, qui expliquent la plupart des échecs :

  • Sérialisation. Arguments et résultats transitent par pickle. Envoyer un DataFrame de 3 Go à huit workers, c'est le sérialiser huit fois : le transfert coûte plus cher que le calcul. Les closures et les lambdas ne sont pas picklables — d'où les erreurs cryptiques au lancement.
  • Méthode de démarrage. spawn (défaut sous Windows et macOS, et sous Linux à partir de 3.14) relance un interpréteur neuf : le module est réimporté, d'où le garde if __name__ == "__main__", sans lequel on obtient une bombe à fourche. fork (historique sous Linux) est plus rapide mais dangereux en présence de threads — un verrou détenu au moment du fork reste verrouillé à jamais dans l'enfant.
  • Coût fixe. Compter quelques dizaines à quelques centaines de millisecondes par processus créé. Paralléliser des tâches de 5 ms est perdant ; d'où chunksize, qui regroupe les tâches en paquets.

Pour les gros tableaux NumPy partagés en lecture, on évite la copie avec multiprocessing.shared_memory (ou joblib, qui bascule automatiquement en memmap au-delà d'un mégaoctet) :

Python
from joblib import Parallel, delayed

# n_jobs=-1 : tous les cœurs. Les gros tableaux sont mémoire-mappés, pas copiés.
scores = Parallel(n_jobs=-1, backend="loky")(
    delayed(evaluer_pli)(X, y, pli) for pli in plis
)

7.5 asyncio : un seul thread, des milliers d'attentes

asyncio ne parallélise rien : il entrelace. Une boucle d'événements exécute une coroutine jusqu'à son prochain await, qui signale « j'attends », et passe la main. Le gain est le même qu'avec des threads pour de l'I/O, mais sans le coût d'un thread système par tâche — on tient des dizaines de milliers de connexions simultanées.

Python
import asyncio, httpx

async def recuperer(client: httpx.AsyncClient, url: str, sem: asyncio.Semaphore) -> dict:
    async with sem:                                  # borne la charge sur le serveur distant
        r = await client.get(url, timeout=10)
        r.raise_for_status()
        return r.json()

async def main(urls: list[str]) -> list[dict]:
    sem = asyncio.Semaphore(20)                      # 20 requêtes en vol au maximum
    async with httpx.AsyncClient() as client:
        taches = [recuperer(client, u, sem) for u in urls]
        return await asyncio.gather(*taches, return_exceptions=True)

resultats = asyncio.run(main(urls))

Le point de vigilance est la contagion : une fonction async ne peut être appelée que depuis du code async. Et un seul appel bloquant (un requests.get, un time.sleep, un calcul NumPy long) gèle toute la boucle, donc toutes les tâches en cours. La porte de sortie est asyncio.to_thread(fonction_bloquante, ...), qui délègue l'appel à un thread. C'est exactement le mécanisme qui permet à FastAPI de servir un modèle scikit-learn sans bloquer le serveur (module 2).

7.6 Le piège qui coûte le plus cher : la sursouscription

Diagnostic classique. Un cross_val_score(..., n_jobs=8) sur une machine à 8 cœurs, où chaque processus lance un BLAS lui-même configuré sur 8 threads : 64 threads se disputent 8 cœurs. Les changements de contexte et la contention de cache font que le résultat est souvent plus lent que la version séquentielle. Le remède : brider les threads natifs quand on parallélise au niveau des processus.
bash / Python
# à placer AVANT l'import de numpy — les bibliothèques lisent ces variables au chargement
export OMP_NUM_THREADS=1
export OPENBLAS_NUM_THREADS=1
export MKL_NUM_THREADS=1

# ou, plus finement, par bloc de code :
from threadpoolctl import threadpool_limits
with threadpool_limits(limits=1, user_api="blas"):
    scores = cross_val_score(modele, X, y, cv=5, n_jobs=8)

La règle générale : un seul niveau de parallélisme à la fois. Soit on parallélise les plis de validation croisée et le BLAS est mono-thread, soit on laisse le BLAS travailler et on garde n_jobs=1. Le bon réglage se mesure, il ne se devine pas.

7.7 Récapitulatif

quoi utiliser quand
Type de charge              Outil                      Parallélisme réel
─────────────────────────────────────────────────────────────────────────
Requêtes HTTP, BDD          asyncio / httpx            oui (entrelacement)
I/O avec lib bloquante      ThreadPoolExecutor         oui (GIL relâché)
Boucles Python pures        ProcessPoolExecutor        oui (N processus)
CV, grid search sklearn     joblib (n_jobs)            oui (loky)
NumPy / PyTorch / polars    rien à faire               oui (BLAS / Rayon)
Boucle Python + threads     ThreadPoolExecutor         NON — GIL
Données > RAM               Dask (module 3)            oui (out-of-core)

Ce qu'il faut retenir du module

  • UV + pyproject.toml + uv.lock : un environnement reproductible en une commande.
  • Le code réutilisable vit dans src/, jamais dans un notebook.
  • Annotations et tests aux frontières ; tester la plomberie, pas la performance du modèle.
  • Jamais de données ni de modèles dans Git ; jamais de réécriture d'historique publié.
  • I/O → threads ou asyncio ; calcul Python pur → processus ; calcul NumPy → déjà parallèle, et surtout ne pas empiler les niveaux de parallélisme.
