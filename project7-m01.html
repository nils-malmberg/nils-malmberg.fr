1. Structure d'un projet Python

Le problème

Un projet de data science commence toujours de la même façon : un notebook, quelques cellules, un résultat. Puis on veut relancer l'analyse sur de nouvelles données, et on s'aperçoit que le résultat dépendait de l'ordre dans lequel les cellules ont été exécutées, qu'une variable a été modifiée à la main entre deux essais, et que la fonction de nettoyage existe en trois versions dans trois notebooks différents. Le code n'est plus reproductible, et personne ne sait laquelle des trois versions a produit le modèle en cours d'utilisation.

La discipline qui évite cela tient en une phrase : dès qu'un bout de code est appelé deux fois, il quitte le notebook et devient un module importable. Le notebook reste ce qu'il est — un brouillon interactif, excellent pour regarder les données — et importe la logique au lieu de la contenir.

La disposition standard

arborescence type
mon-projet/
├── pyproject.toml        # identité du projet, dépendances, config des outils
├── uv.lock               # versions exactes installées (versionné dans Git)
├── README.md
├── src/
│   └── mon_projet/       # le paquet importable : import mon_projet
│       ├── __init__.py   # marque le dossier comme paquet (peut être vide)
│       ├── data.py       # chargement / nettoyage
│       ├── features.py   # transformations
│       └── models.py     # entraînement / inférence
├── notebooks/            # exploration ; aucune logique réutilisable ici
├── tests/
└── data/                 # ignoré par Git (voir section 8)

Pourquoi ce dossier src/ intermédiaire, qui semble n'ajouter qu'un niveau de profondeur ? Parce que sans lui, Python trouve le paquet simplement parce qu'il se trouve dans le répertoire courant. On peut alors avoir des tests qui passent alors que le paquet n'est en réalité pas installable — l'erreur n'apparaît que chez quelqu'un d'autre. Avec src/, le paquet n'est importable que s'il a été réellement installé dans l'environnement : ce qu'on teste est exactement ce qu'on distribuera.

Le fichier pyproject.toml

C'est la carte d'identité du projet, au format TOML (un format de configuration lisible, à mi-chemin entre INI et JSON). Il a remplacé l'ancien trio setup.py / setup.cfg / requirements.txt, et il centralise aussi la configuration des outils de qualité.

pyproject.toml, commenté
[project]
name = "mon-projet"                 # nom de distribution (tirets autorisés)
version = "0.1.0"
requires-python = ">=3.12"          # versions de Python acceptées
dependencies = [                    # ce dont le projet a besoin pour FONCTIONNER
    "numpy>=2.0",
    "polars>=1.0",
    "scikit-learn>=1.5",
]

[dependency-groups]                 # ce dont on a besoin pour DÉVELOPPER
dev = ["pytest>=8", "ruff>=0.6", "mypy>=1.11", "pre-commit>=3.8"]

[build-system]                      # comment fabriquer le paquet installable
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]                         # configuration du linter/formateur
line-length = 100

[tool.pytest.ini_options]           # configuration des tests
testpaths = ["tests"]

La distinction entre dependencies et le groupe dev a une conséquence concrète : l'image Docker de production (module 5) n'installe que les premières, ce qui la rend plus légère et réduit sa surface d'attaque.

2. Environnements virtuels et UV

Pourquoi un environnement virtuel

Un seul Python est installé sur la machine, avec un seul jeu de bibliothèques. Deux projets qui ont besoin de versions différentes de pandas ne peuvent donc pas coexister : installer l'un casse l'autre. Un environnement virtuel résout cela en créant un dossier — par convention .venv/ — qui contient sa propre copie de l'interpréteur et ses propres bibliothèques. Chaque projet a son atelier, avec ses outils à lui, et rien de ce qu'on y installe ne déborde sur les autres.

UV en pratique

UV (écrit en Rust par Astral, les auteurs de ruff) remplace à lui seul pip, virtualenv, pyenv, pipx et poetry. Deux différences pratiques : il est un à deux ordres de grandeur plus rapide, et il sait aussi installer les interpréteurs Python eux-mêmes — on n'a plus à se soucier de la version fournie par le système.

cycle de travail courant
# créer un projet : génère pyproject.toml, .venv/ et uv.lock
uv init mon-projet && cd mon-projet

# installer une version précise de Python, sans toucher au Python système
uv python install 3.12
uv python pin 3.12              # fige la version pour ce projet

# ajouter une dépendance : résolution + installation + mise à jour du lock
uv add "polars>=1.0" scikit-learn
uv add --dev pytest ruff mypy pre-commit
uv remove scikit-learn          # retirer proprement

# recréer à l'identique l'environnement d'un collègue, ou celui de la CI
uv sync                         # installe EXACTEMENT ce que dit uv.lock
uv sync --no-dev                # sans les outils de développement (production)

# exécuter dans l'environnement, sans avoir à l'activer
uv run python -m mon_projet.train
uv run pytest
uv run ruff check .

# mettre à jour volontairement
uv lock --upgrade-package polars

# script autonome, dépendances déclarées dans son propre en-tête (PEP 723)
uv run --with pandas,matplotlib analyse.py

Contraintes et lockfile : la différence qui compte

Deux fichiers, deux rôles distincts. Le pyproject.toml déclare des contraintes — « numpy au moins en 2.0 » — c'est-à-dire une intention. Le uv.lock enregistre la solution exacte retenue par le résolveur — numpy 2.1.3, avec l'empreinte cryptographique de chaque fichier téléchargé — c'est-à-dire un état reproductible. Les deux se versionnent dans Git. Résultat : uv sync installe les mêmes octets sur votre machine, sur celle d'un collègue et dans la chaîne d'intégration continue, aujourd'hui comme dans six mois.

C'est la différence avec un requirements.txt produit par pip freeze : celui-ci fige les versions d'une seule plateforme, mélange dépendances directes et indirectes, et ne dit pas lesquelles vous avez demandées.

Le piège CUDA. En ML, ce qui casse la reproductibilité n'est presque jamais Python : c'est le couple pilote GPU / version de CUDA compilée dans les wheels de PyTorch. UV sait pointer un index alternatif (section [tool.uv.sources] vers le dépôt cu124, par exemple), mais l'environnement « identique » s'arrête à la frontière de la machine. C'est une des raisons de passer à Docker dès qu'un GPU entre en jeu (module 5).

Et conda ? Il reste utile quand on dépend de bibliothèques système non-Python compliquées à compiler (GDAL, certains solveurs, une MKL configurée finement). Pour un projet de ML standard, UV est plus rapide, plus simple, et son lockfile est nettement plus fiable qu'un environment.yml.

3. Les décorateurs, de zéro

Le problème qu'ils résolvent

Supposons que l'on veuille chronométrer trois fonctions d'entraînement. La solution naïve consiste à copier deux lignes de mesure au début et à la fin de chacune. C'est répétitif, ça mélange la mesure et la logique métier, et le jour où l'on veut aussi journaliser les arguments, il faut repasser partout.

Un décorateur est la réponse de Python à ce problème : une façon d'emballer une fonction dans une autre qui ajoute un comportement avant et après, sans modifier une seule ligne de la fonction d'origine. L'image est celle d'un colis qu'on emballe : le contenu ne change pas, mais tout ce qui passe par l'emballage peut être compté, tracé, mis en cache.

Le mécanisme, en trois temps

Premier point à admettre : en Python, une fonction est une valeur comme une autre. On peut la mettre dans une variable, la passer en argument, la renvoyer.

Python — les fonctions sont des objets
def bonjour(nom):
    return f"Bonjour {nom}"

f = bonjour              # pas d'appel : on manipule la fonction elle-même
print(f("Nils"))         # Bonjour Nils
print(bonjour.__name__)  # bonjour  → une fonction a des attributs

Deuxième point : on peut donc écrire une fonction qui prend une fonction et en renvoie une nouvelle.

Python — un décorateur écrit à la main, sans sucre syntaxique
import time

def chrono(fonction):                     # reçoit la fonction à emballer
    def emballage(*args, **kwargs):       # la nouvelle fonction qui la remplacera
        debut = time.perf_counter()
        resultat = fonction(*args, **kwargs)   # on appelle l'originale
        duree = time.perf_counter() - debut
        print(f"{fonction.__name__} : {duree:.3f} s")
        return resultat                   # on renvoie SON résultat, inchangé
    return emballage                      # on renvoie l'emballage, pas son appel

def entrainer(n):
    time.sleep(n)
    return "modèle"

entrainer = chrono(entrainer)             # on remplace la fonction par sa version emballée
entrainer(0.5)                            # entrainer : 0.500 s

*args et **kwargs signifient « tous les arguments positionnels » et « tous les arguments nommés » : ils permettent à l'emballage d'accepter n'importe quelle signature et de la transmettre telle quelle. Sans eux, le décorateur ne fonctionnerait que pour des fonctions à un seul argument.

Troisième point : la ligne entrainer = chrono(entrainer) est si fréquente que Python lui donne une notation dédiée, le @. Les deux écritures ci-dessous sont rigoureusement équivalentes :

Python — avant / après
# AVANT : réécriture explicite
def entrainer(n): ...
entrainer = chrono(entrainer)

# APRÈS : la même chose, en une ligne au-dessus de la définition
@chrono
def entrainer(n): ...

Le détail qui manque : functools.wraps

Tel qu'écrit plus haut, le décorateur remplace la fonction par emballage : entrainer.__name__ vaut désormais "emballage", la docstring a disparu, et les outils de débogage affichent le mauvais nom. @functools.wraps(fonction), posé sur l'emballage, recopie ces métadonnées. Ce n'est pas optionnel — sans lui, les messages d'erreur deviennent trompeurs.

import functools

def chrono(fonction):
    @functools.wraps(fonction)            # conserve nom, docstring, annotations
    def emballage(*args, **kwargs):
        ...
    return emballage

Les décorateurs de la bibliothèque standard

On en écrit rarement ; on en utilise constamment. Voici ceux qu'il faut reconnaître :

Python — @property : un attribut calculé
class Jeu:
    def __init__(self, X, y):
        self.X, self.y = X, y

    @property
    def taille(self):                     # se lit comme un attribut, se calcule à la demande
        return len(self.y)

    @property
    def taux_positifs(self):
        return float(self.y.mean())

jeu = Jeu(X, y)
print(jeu.taille)          # PAS jeu.taille() : le @property fait l'appel pour nous
print(jeu.taux_positifs)

L'intérêt : on expose une valeur calculée avec la même syntaxe qu'un attribut stocké. On peut donc transformer un attribut simple en valeur calculée plus tard, sans casser le code qui l'utilise. C'est aussi ce qui permet d'ajouter une validation à l'écriture, via un @taille.setter.

Python — les autres décorateurs à connaître
import functools

class Modele:
    @staticmethod                 # fonction rangée dans la classe, sans accès à self
    def normaliser(x):
        return (x - x.mean()) / x.std()

    @classmethod                  # reçoit la CLASSE : sert de constructeur alternatif
    def depuis_fichier(cls, chemin):
        return cls(**json.load(open(chemin)))

@functools.cache                  # mémorise les résultats : appel suivant = instantané
def charger_referentiel(annee: int):
    return pd.read_parquet(f"ref_{annee}.parquet")

@functools.lru_cache(maxsize=1024)   # idem, mais avec une taille de cache bornée
def distance(a: str, b: str) -> float:
    ...

Le cache mérite une mise en garde : il garde les résultats en mémoire pour toute la durée du programme et exige des arguments hachables (donc pas de liste ni de DataFrame). Sur une fonction qui charge un gros fichier, c'est exactement ce qu'on veut ; sur une fonction appelée avec des millions d'arguments différents, c'est une fuite de mémoire.

Le même mécanisme se retrouve partout dans l'écosystème : @pytest.fixture et @pytest.mark.parametrize (section 7), @app.get("/items") dans FastAPI (module 6), @task dans les orchestrateurs, @numba.njit pour compiler une boucle. Savoir lire un @ comme « cette fonction est emballée par ceci » suffit à comprendre ces bibliothèques.

4. Dataclasses : frozen, slots et le reste

Le problème

Regroupons trois paramètres d'entraînement dans une classe ordinaire. Il faut écrire un constructeur qui recopie chaque argument dans un attribut, puis une méthode d'affichage lisible, puis une comparaison — sinon deux configurations identiques seront considérées comme différentes. Cela donne une trentaine de lignes de code répétitif pour transporter trois valeurs.

Python — AVANT : classe écrite à la main
class TrainConfig:
    def __init__(self, data_path, n_estimators=300, learning_rate=0.05, random_state=42):
        self.data_path = data_path
        self.n_estimators = n_estimators
        self.learning_rate = learning_rate
        self.random_state = random_state

    def __repr__(self):
        return (f"TrainConfig(data_path={self.data_path!r}, "
                f"n_estimators={self.n_estimators}, "
                f"learning_rate={self.learning_rate}, "
                f"random_state={self.random_state})")

    def __eq__(self, autre):
        if not isinstance(autre, TrainConfig):
            return NotImplemented
        return (self.data_path, self.n_estimators, self.learning_rate, self.random_state) == \
               (autre.data_path, autre.n_estimators, autre.learning_rate, autre.random_state)
Python — APRÈS : le décorateur @dataclass écrit tout cela
from dataclasses import dataclass, field
from pathlib import Path

@dataclass
class TrainConfig:
    data_path: Path                        # pas de valeur par défaut : argument obligatoire
    n_estimators: int = 300
    learning_rate: float = 0.05
    random_state: int | None = 42

cfg = TrainConfig(Path("data/train.parquet"), learning_rate=0.1)
print(cfg)        # TrainConfig(data_path=PosixPath('data/train.parquet'),
                  #             n_estimators=300, learning_rate=0.1, random_state=42)
cfg == TrainConfig(Path("data/train.parquet"), learning_rate=0.1)   # True

Le décorateur lit les annotations de la classe et génère pour nous __init__, __repr__ et __eq__. Une remarque importante : ici, les annotations de type ne sont pas décoratives — c'est leur présence qui déclenche la génération du champ. C'est l'un des rares endroits où le typage a un effet réel à l'exécution.

Les options utiles

Python — @dataclass(frozen=True, slots=True)
@dataclass(frozen=True, slots=True)
class TrainConfig:
    data_path: Path
    n_estimators: int = 300
    learning_rate: float = 0.05
    features: tuple[str, ...] = ()         # tuple, pas list : voir plus bas

frozen=True — l'objet devient immuable. Toute tentative de modification lève une erreur au lieu de passer inaperçue :

cfg.learning_rate = 0.5
# FrozenInstanceError: cannot assign to field 'learning_rate'

Pourquoi vouloir cela ? Parce qu'une configuration qui change en cours d'exécution est une source de bugs irreproductibles : on lance un entraînement, une fonction modifie discrètement un paramètre au passage, et le résultat ne correspond plus à ce qu'on croit avoir demandé. Une configuration figée est une garantie que ce qu'on a lu au début est ce qui a servi jusqu'au bout. Bénéfice secondaire : un objet immuable est hachable, donc utilisable comme clé de dictionnaire ou argument d'une fonction mise en cache (section 3). Pour obtenir une variante, on ne modifie pas : on copie en changeant ce qu'il faut, avec dataclasses.replace(cfg, learning_rate=0.1).

slots=True — attributs fixés d'avance. Par défaut, chaque objet Python porte un dictionnaire interne (__dict__) qui associe des noms d'attributs à des valeurs, ce qui permet d'en ajouter n'importe quand. C'est souple, mais cela coûte de la mémoire et laisse passer les fautes de frappe :

# sans slots : la faute de frappe crée un NOUVEL attribut, en silence
cfg.learnig_rate = 0.1        # aucune erreur ; le vrai paramètre n'a pas bougé

# avec slots=True : la liste des attributs est figée à la création de la classe
cfg.learnig_rate = 0.1
# AttributeError: 'TrainConfig' object has no attribute 'learnig_rate'

L'économie de mémoire (souvent 30 à 40 % par instance) ne compte que si l'on crée des millions d'objets ; la détection des fautes de frappe, elle, sert tous les jours.

Le piège des valeurs par défaut mutables. Écrire features: list[str] = [] lève une erreur, et c'est une bonne nouvelle : la liste serait créée une seule fois et partagée par toutes les instances — un classique des bugs Python. Deux solutions : un type immuable (tuple[str, ...] = ()), ou field(default_factory=list), qui construit une liste neuve à chaque instance.
Python — les autres options, avec leur usage
from dataclasses import dataclass, field, asdict, replace

@dataclass(frozen=True, slots=True, order=True, kw_only=True)
class Resultat:
    rmse: float
    modele: str
    # exclu de la comparaison et de l'affichage (par exemple un gros objet) :
    predictions: list = field(default_factory=list, compare=False, repr=False)

    def __post_init__(self):              # appelé après l'init généré : validation
        if self.rmse < 0:
            raise ValueError("un RMSE ne peut pas être négatif")

r = Resultat(rmse=0.42, modele="gbm")     # kw_only : arguments NOMMÉS obligatoires
sorted([r1, r2, r3])                      # order=True : comparaison champ par champ
asdict(r)                                 # → dict, prêt pour json.dumps ou MLflow
replace(r, modele="xgb")                  # copie modifiée (l'original est figé)

Deux cousines à connaître : typing.NamedTuple, plus légère mais limitée à un tuple immuable, et pydantic, qui ressemble beaucoup à une dataclass mais vérifie et convertit les types à l'exécution. La règle de choix : dataclass pour les objets internes au code, pydantic dès que les données viennent de l'extérieur — fichier de configuration, requête HTTP, réponse d'API. C'est le socle de FastAPI, détaillé au module 6.

5. Les annotations de type

Ce que c'est, et ce que ce n'est pas

Une annotation comme def rmse(y: np.ndarray) -> float est une métadonnée. Python ne la vérifie pas à l'exécution : passer une chaîne de caractères à cette fonction ne déclenchera aucune erreur de typage (seulement, plus loin, une erreur incompréhensible). Les annotations servent à trois choses : un vérificateur statique (mypy, pyright) qui lit le code sans l'exécuter et signale les incohérences, l'éditeur qui propose l'autocomplétion et détecte les fautes, et le lecteur, pour qui la signature devient une documentation qui ne peut pas mentir trop longtemps.

Python — la syntaxe utile en pratique
from collections.abc import Iterable, Callable, Sequence
from pathlib import Path
import numpy as np
from numpy.typing import NDArray

def charger(chemin: Path) -> pd.DataFrame: ...

def normaliser(x: NDArray[np.float64]) -> NDArray[np.float64]: ...

def selectionner(noms: Sequence[str], seuil: float = 0.5) -> list[str]: ...

# "peut valoir None" : le | remplace l'ancien Optional[...]
def charger_modele(chemin: Path | None = None) -> Modele | None: ...

# une fonction en argument
def appliquer(f: Callable[[float], float], valeurs: Iterable[float]) -> list[float]:
    return [f(v) for v in valeurs]

# un dictionnaire dont on connaît les clés
scores: dict[str, float] = {"rmse": 0.42, "mae": 0.31}

Où le typage rapporte, et où il coûte

Le rendement est maximal aux frontières : signatures des fonctions publiques, objets de configuration, structures de données échangées entre modules. Il est faible à l'intérieur d'un calcul numérique, où annoter chaque variable intermédiaire alourdit sans rien apporter. Et il faut connaître sa limite principale : NDArray[np.float64] ne dit rien de la forme du tableau, qui est pourtant la première source d'erreurs en ML. D'où l'habitude de documenter la forme attendue en commentaire — (n_samples, n_features) — et de la vérifier par un assert X.ndim == 2 en début de fonction.

6. Itérateurs et générateurs

Le problème

Un fichier de journaux de 40 Go, une machine avec 16 Go de RAM. La ligne lignes = open("events.jsonl").readlines() échoue par manque de mémoire, parce qu'elle construit la liste complète avant d'en traiter le premier élément. Il faut une façon de produire les données au fur et à mesure : un distributeur qui fabrique à la demande, plutôt qu'un entrepôt qu'on remplit d'abord.

Itérable et itérateur : deux notions distinctes

Un itérable est un objet sur lequel on peut faire une boucle for (une liste, un dictionnaire, un fichier). Un itérateur est l'objet qui garde la position courante et sait donner l'élément suivant. La boucle for cache ce mécanisme : elle demande d'abord un itérateur à l'itérable, puis lui réclame les éléments un par un jusqu'à épuisement.

Python — ce que fait réellement une boucle for
nombres = [10, 20, 30]

it = iter(nombres)      # on demande un itérateur à l'itérable
print(next(it))         # 10
print(next(it))         # 20
print(next(it))         # 30
print(next(it))         # StopIteration : c'est le signal de fin, que for intercepte

# la boucle ci-dessous est exactement équivalente à ce qui précède
for n in nombres:
    print(n)

Écrire son propre itérateur (la version longue)

Pour comprendre ce que les générateurs automatisent, écrivons d'abord un itérateur « à la main ». Il suffit d'implémenter deux méthodes : __iter__, qui renvoie l'itérateur lui-même, et __next__, qui renvoie l'élément suivant ou lève StopIteration.

Python — un itérateur de lots, écrit explicitement
class Lots:
    """Découpe une séquence en lots de taille fixe."""

    def __init__(self, donnees, taille):
        self.donnees = donnees
        self.taille = taille
        self.position = 0          # l'ÉTAT que l'itérateur doit mémoriser

    def __iter__(self):
        return self                # l'objet est son propre itérateur

    def __next__(self):
        if self.position >= len(self.donnees):
            raise StopIteration    # plus rien à donner : fin de la boucle
        lot = self.donnees[self.position : self.position + self.taille]
        self.position += self.taille
        return lot

for lot in Lots(list(range(10)), 3):
    print(lot)                     # [0,1,2] puis [3,4,5] puis [6,7,8] puis [9]

Le générateur : le même résultat en quatre lignes

Une fonction qui contient le mot-clé yield ne se comporte plus comme une fonction ordinaire. L'appeler n'exécute rien : cela renvoie un générateur. À chaque next(), le corps s'exécute jusqu'au prochain yield, renvoie la valeur, puis se met en pause en conservant tout son état local — variables et position dans le code. L'appel suivant reprend exactement là où on s'était arrêté.

Python — le même itérateur, en générateur
def lots(donnees, taille):
    for debut in range(0, len(donnees), taille):
        yield donnees[debut : debut + taille]      # pause ici, reprise au prochain appel

for lot in lots(list(range(10)), 3):
    print(lot)                                     # résultat identique

Le générateur écrit pour nous __iter__, __next__, la gestion de l'état et le StopIteration final. Observons la mise en pause pas à pas :

Python — la mécanique du yield, étape par étape
def trace():
    print("  → début du corps")
    yield 1
    print("  → reprise après le premier yield")
    yield 2
    print("  → reprise après le second yield")

g = trace()            # RIEN ne s'affiche : le corps n'a pas encore démarré
print(next(g))         #   → début du corps        puis affiche 1
print(next(g))         #   → reprise après ...     puis affiche 2
next(g)                #   → reprise après ...     puis StopIteration

Application : traiter un fichier plus gros que la mémoire

Python — un pipeline de générateurs
import json, itertools
from collections.abc import Iterator

def lire_lignes(chemin: str) -> Iterator[dict]:
    """Une ligne en mémoire à la fois, quelle que soit la taille du fichier."""
    with open(chemin, encoding="utf-8") as f:
        for ligne in f:                 # un fichier ouvert EST déjà un itérateur
            yield json.loads(ligne)

def valides(evenements: Iterator[dict]) -> Iterator[dict]:
    """Filtre, sans rien matérialiser."""
    for e in evenements:
        if e.get("prix") and e["prix"] > 0:
            yield e

def par_lots(iterable, taille: int):
    """Regroupe en lots — indispensable pour l'inférence batchée (module 6)."""
    it = iter(iterable)
    while lot := list(itertools.islice(it, taille)):   # := affecte ET teste
        yield lot

# les trois générateurs se chaînent : la mémoire reste en O(taille du lot)
flux = par_lots(valides(lire_lignes("events.jsonl")), 1024)
for lot in flux:
    scores = modele.predict(lot)

Rien n'est exécuté tant qu'on ne consomme pas le flux : c'est l'évaluation paresseuse. Chaque lot traverse les trois étapes à la demande, et la mémoire ne dépend que de la taille du lot. En Python 3.12+, itertools.batched fait le travail de par_lots nativement.

Python — les compléments utiles
# expression génératrice : comme une compréhension de liste, mais paresseuse
carres = (x ** 2 for x in range(10_000_000))    # rien n'est calculé ni stocké
total = sum(carres)                             # calcul au fil de la consommation

# yield from : déléguer à un autre générateur (aplatissement, composition)
def tous_les_fichiers(dossiers):
    for d in dossiers:
        yield from lire_lignes(d)

# générateur infini : parfaitement légitime, tant qu'on le borne à la consommation
def compteur(debut=0):
    n = debut
    while True:
        yield n
        n += 1

premiers = list(itertools.islice(compteur(), 5))     # [0, 1, 2, 3, 4]

# itertools : groupby, chain, product, accumulate, tee — tous paresseux
for cle, groupe in itertools.groupby(sorted(lignes, key=cle_ville), key=cle_ville):
    print(cle, sum(1 for _ in groupe))
Un générateur ne se parcourt qu'une fois. Après consommation, il est épuisé : une seconde boucle ne produira rien, silencieusement. De même, len() et l'indexation n'existent pas sur un générateur, puisqu'on ignore combien d'éléments restent. Si l'on a besoin de plusieurs passages, il faut soit matérialiser avec list(...) — en acceptant le coût mémoire —, soit relancer le générateur depuis sa source.

7. Qualité : ruff, pytest, pre-commit

ruff : formatage et analyse statique

ruff remplace flake8, isort, black et une bonne partie de pylint, en une fraction du temps. Deux usages complémentaires : check signale les erreurs probables (import inutilisé, variable jamais lue, comparaison suspecte) et format réécrit le code dans un style unique.

uv run ruff check --fix .        # signale et corrige ce qui peut l'être
uv run ruff format .             # formatage automatique
uv run mypy src/                 # vérification des types

Le formatage automatique n'est pas une coquetterie : il supprime les différences de style dans les diffs, qui polluent les revues et masquent les vrais changements.

pytest : tester du code de data science

La question n'est pas « comment écrire un test » mais « que faut-il tester ». On ne teste pas « le modèle atteint 92 % d'accuracy » — cela dépend des données et relève du suivi en production (module 25). On teste la plomberie : les formes, les cas dégénérés, le déterminisme, les invariants métier.

tests/test_features.py
import numpy as np
import pytest
from mon_projet.features import ajouter_features_temporelles, entrainer

pre-commit : automatiser les vérifications

Le problème. Les outils précédents ne servent que si on pense à les lancer. En pratique, on oublie, et le code mal formaté ou cassé entre dans l'historique Git ; la chaîne d'intégration continue le signale dix minutes plus tard, et il faut un commit supplémentaire pour corriger.

La solution. Git sait déclencher des scripts à certains moments de son cycle — ce sont les hooks. pre-commit est un outil qui installe un hook déclenché avant chaque commit, lance les vérifications sur les seuls fichiers modifiés, et annule le commit si quelque chose ne va pas. Le code fautif n'entre jamais dans l'historique.

installation, une fois par projet
uv add --dev pre-commit
uv run pre-commit install        # écrit le hook dans .git/hooks/pre-commit

# vérifier tout le dépôt (utile la première fois, ou en CI)
uv run pre-commit run --all-files

# mettre à jour les versions des outils déclarés
uv run pre-commit autoupdate
.pre-commit-config.yaml, commenté
repos:
  # ── hooks génériques, fournis par pre-commit lui-même ──
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace        # supprime les espaces en fin de ligne
      - id: end-of-file-fixer          # garantit un saut de ligne final
      - id: check-yaml                 # valide la syntaxe des fichiers YAML
      - id: check-added-large-files    # REFUSE les fichiers volumineux
        args: ["--maxkb=5000"]         #   → empêche de committer un CSV par erreur
      - id: check-merge-conflict       # détecte les marqueurs de conflit oubliés
      - id: detect-private-key         # refuse une clé privée committée

  # ── lint et formatage ──
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format

  # ── types ──
  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.11.2
    hooks:
      - id: mypy
        additional_dependencies: [numpy, pandas-stubs]

  # ── notebooks : retire les sorties avant commit ──
  - repo: https://github.com/kynan/nbstripout
    rev: 0.7.1
    hooks:
      - id: nbstripout

Deux hooks méritent qu'on s'y arrête. check-added-large-files est la meilleure protection contre l'erreur la plus coûteuse d'un projet data — committer un jeu de données (section 8). nbstripout retire les sorties des notebooks : sans lui, chaque exécution produit un diff de plusieurs milliers de lignes illisibles, et les images encodées font gonfler le dépôt indéfiniment.

Un dernier détail pratique : git commit --no-verify contourne les hooks. C'est utile dans une urgence, et c'est aussi la raison pour laquelle les mêmes vérifications doivent tourner dans la chaîne d'intégration continue, où personne ne peut les contourner (module 25).

8. Git pour un projet data

Le workflow que j'utilise, volontairement minimal : main toujours fonctionnelle, une branche par sujet, une pull request même en solo — elle force une relecture du diff complet, ce qui attrape beaucoup d'erreurs.

bash
git switch -c feat/gradient-boosting     # créer et basculer sur une branche
git add -p                               # relire chaque morceau avant de l'indexer
git commit -m "feat(model): baseline XGBoost, RMSE 0.42 en CV"

git fetch origin
git rebase origin/main                   # historique linéaire AVANT publication
git push -u origin feat/gradient-boosting

git log --oneline --graph -15            # visualiser l'historique
git diff main...HEAD                     # tout ce que la branche apporte

Rebase ou merge ? Rebase tant que la branche est privée : l'historique reste linéaire et lisible. Merge dès qu'elle est partagée : réécrire des commits que quelqu'un a déjà récupérés casse son dépôt. La règle tient en une phrase — ne jamais réécrire un historique déjà publié.

Les messages suivent la convention Conventional Commits (feat:, fix:, refactor:, docs:) : cela permet de générer un changelog et, surtout, de retrouver pourquoi une transformation a été ajoutée six mois plus tard.

Git n'est pas fait pour les données. Un CSV de 2 Go committé reste dans l'historique pour toujours, même supprimé ensuite : chaque clone le retéléchargera. Mettez data/, *.csv, *.parquet, *.pkl, models/, .venv/ et .ipynb_checkpoints/ dans .gitignore dès le premier commit. Pour versionner données et modèles, voir DVC au module 25.

Ce qu'il faut retenir du module

  • Le code réutilisable vit dans src/, jamais dans un notebook ; pyproject.toml centralise tout.
  • UV donne un environnement reproductible en une commande : contraintes dans pyproject.toml, solution exacte dans uv.lock, les deux versionnés.
  • Un décorateur est une fonction qui en emballe une autre ; @ est un raccourci pour f = decorateur(f).
  • @dataclass génère le code répétitif ; frozen=True protège des mutations silencieuses, slots=True des fautes de frappe.
  • Les annotations ne sont pas vérifiées à l'exécution : elles servent aux outils et au lecteur, surtout aux frontières.
  • yield met une fonction en pause en conservant son état : c'est ce qui permet de traiter des données plus grosses que la mémoire.
  • pre-commit empêche le code mal formé d'entrer dans l'historique, et un jeu de données d'y entrer du tout.
