Data science en pratique : du problème au dataset

Dans un projet réel, le choix de l'algorithme occupe une fraction marginale du temps et explique une fraction marginale de la performance. Ce qui fait la différence, c'est le cadrage du problème, la qualité des données et la rigueur du protocole d'évaluation. Ce module couvre exactement cette partie-là — celle qu'on n'apprend pas dans les cours d'algorithmes.

1. Cycle de vie d'un projet

les étapes, et leur poids réel en temps
1. Cadrage métier          définir la question, la métrique, ce qu'on fera du résultat   ~10 %
2. Collecte / accès        trouver, extraire, joindre les données                        ~20 %
3. Exploration            comprendre les données, détecter les anomalies                 ~15 %
4. Préparation            nettoyage, features, encodages                                 ~25 %
5. Modélisation           baseline, puis itérations                                      ~10 %
6. Évaluation             protocole, métriques, analyse d'erreurs                        ~10 %
7. Déploiement / suivi    mise en production, monitoring, ré-entraînement                ~10 %

Le cycle n'est pas linéaire : l'exploration révèle des problèmes de collecte, l'analyse d'erreurs renvoie au feature engineering, et le déploiement fait apparaître des contraintes de latence qui invalident un modèle. La seule erreur structurelle est de traiter ces étapes comme un tunnel à sens unique.

La question à poser avant tout le reste

Quelle décision sera prise différemment grâce à ce modèle ? Si personne ne sait répondre, le projet produira un notebook et rien d'autre. Cette question détermine tout le reste : la métrique (un coût d'erreur asymétrique change le seuil), la latence acceptable (temps réel ou lot nocturne), le besoin d'explicabilité (un refus de crédit doit être motivé), et même la faisabilité — certaines décisions ont besoin de causalité, pas de prédiction (module 8).

2. Cadrage : la cible et la baseline

Définir la cible est plus subtil qu'il n'y paraît. Prédire « le churn » exige de fixer une fenêtre (résiliation dans les 30 jours ? 90 ?), une date d'observation, et le sort des cas ambigus (un client inactif est-il parti ?). Deux définitions raisonnables peuvent donner des taux de positifs allant du simple au triple, et donc des modèles incomparables.

Fixer l'unité d'observation : une ligne = un client ? un client-mois ? une transaction ? Ce choix détermine la structure de dépendance des données, donc le schéma de validation (section 8).

Établir une baseline, enfin, avant tout modèle : la moyenne pour une régression, la classe majoritaire pour une classification, la valeur de la veille pour une série temporelle, ou la règle métier existante. Sans elle, un R² de 0,7 ne veut rien dire — il peut être excellent ou ridicule selon le problème. La baseline donne aussi le coût réel du projet : si une règle à trois conditions atteint 95 % de la performance du modèle, le modèle ne vaut peut-être pas sa complexité opérationnelle.

3. Exploration : une checklist

ce que je regarde systématiquement
Structure      dimensions, types, mémoire, granularité (une ligne = quoi ?)
Cible          distribution, taux de positifs, valeurs extrêmes, évolution dans le temps
Manquants      taux par colonne, structure des manquants (voir section 5)
Doublons       lignes identiques ET doublons sur la clé métier
Cardinalité    colonnes constantes (inutiles), identifiants déguisés (dangereux)
Distributions  asymétrie, multimodalité, valeurs impossibles (âge = 200, prix négatif)
Temps          couverture, trous, saisonnalité, ruptures (changement de collecte ?)
Relations      corrélations entre features, lien de chaque feature avec la cible
Groupes        déséquilibres entre segments, sous-populations sous-représentées
Python
import polars as pl

df = pl.read_parquet("data/clients.parquet")

print(df.describe())                                    # stats de base par colonne
print(df.null_count())                                  # manquants par colonne
print(df.select(pl.all().n_unique()))                   # cardinalités
print(df.filter(pl.struct(df.columns).is_duplicated())) # doublons exacts

# valeurs impossibles : toujours confronter aux bornes métier
print(df.filter((pl.col("age") < 0) | (pl.col("age") > 120)))

Les outils de profilage automatique (ydata-profiling, skrub) produisent en une ligne un rapport complet. Utiles pour débroussailler, ils ne remplacent pas le regard métier : seule une connaissance du domaine dit qu'un prix à 0,01 € correspond à un test interne, ou qu'une valeur « 9999 » est un code de saisie signifiant « inconnu ».

L'identifiant déguisé. Une colonne de très forte cardinalité corrélée à la cible est presque toujours un piège : numéro de dossier attribué séquentiellement, code produit encodant la catégorie, date d'export. Un arbre l'exploitera parfaitement en validation et s'effondrera en production. Quand une feature semble trop belle, c'est généralement qu'elle contient une information qui n'existera pas au moment de la prédiction (section 9).

4. Visualisation utile

Trois bibliothèques couvrent tous les besoins : matplotlib (contrôle total, verbeux), seaborn (statistique, concis, excellent par défaut), plotly (interactif, précieux pour explorer un nuage de points dense). Quelques principes qui changent réellement la lisibilité :

  • Un histogramme cache autant qu'il montre : le nombre de classes change complètement l'allure. Doubler avec un violin plot ou un strip plot quand l'échantillon est petit.
  • Sur des données asymétriques, passer en échelle log — sinon 99 % des points s'écrasent dans le premier centimètre du graphique.
  • Contre la surimpression (des millions de points), utiliser la transparence, un échantillon, ou une carte de densité (hexbin).
  • Toujours tracer la cible en fonction du temps : c'est le graphique qui révèle les ruptures de collecte, les changements de définition et la dérive (module 24).
  • Se méfier des moyennes : le quartet d'Anscombe et le « datasaurus » rappellent que des jeux de données de statistiques identiques peuvent être radicalement différents. Regarder les distributions, pas les résumés.

5. Données manquantes

Avant de choisir une méthode, il faut comprendre pourquoi une valeur manque. La typologie de Rubin :

  • MCAR (missing completely at random) — le manque est indépendant de tout : capteur tombé en panne au hasard. Supprimer les lignes ne biaise rien, on perd seulement de la puissance.
  • MAR (missing at random) — le manque dépend des variables observées : les revenus manquent plus souvent chez les jeunes, et l'âge est connu. L'imputation conditionnelle est légitime.
  • MNAR (missing not at random) — le manque dépend de la valeur elle-même : les hauts revenus refusent de répondre. Aucune imputation ne corrige cela ; il faut modéliser le mécanisme, ou au minimum documenter le biais.
stratégies
Supprimer les lignes      acceptable si < 5 % et MCAR. Sinon on biaise l'échantillon.
Supprimer la colonne      si > 60-70 % manquants ET aucun signal dans le fait de manquer.
Moyenne / médiane         rapide ; réduit artificiellement la variance et écrase les corrélations.
KNN / itératif (MICE)     impute à partir des autres colonnes ; coûteux mais bien meilleur.
Valeur sentinelle         -1, "inconnu" : parfait pour les modèles à base d'arbres.
Ne rien faire             HistGradientBoosting, XGBoost et LightGBM gèrent nativement les NaN,
                          et apprennent la meilleure direction pour les valeurs absentes.
Indicateur de manque      ajouter une colonne booléenne : le FAIT de manquer est souvent
                          lui-même informatif (un client qui ne renseigne pas son revenu...).
Python
from sklearn.experimental import enable_iterative_imputer   # noqa: F401
from sklearn.impute import IterativeImputer, SimpleImputer

# imputation multivariée : chaque colonne est prédite à partir des autres, en boucle
imp = IterativeImputer(max_iter=10, random_state=0)

# conserver l'information "cette valeur manquait"
imp_simple = SimpleImputer(strategy="median", add_indicator=True)
L'imputation appartient au pipeline. Calculer une médiane sur l'ensemble des données avant le découpage train/test fait entrer de l'information du test dans l'entraînement. L'imputeur doit être ajusté sur le pli d'entraînement et appliqué au reste — ce que garantit un Pipeline (module 3).

6. Feature engineering

C'est l'étape au meilleur rendement sur données tabulaires : une bonne feature bat presque toujours un meilleur algorithme. L'idée générale est d'encoder la connaissance métier sous une forme que le modèle peut exploiter.

Variables catégorielles

encodages
One-hot          une colonne par modalité. Défaut sûr. Explose si cardinalité élevée.
Ordinal          entier par modalité. Uniquement si un ORDRE existe réellement
                 (S < M < L), ou pour des modèles à base d'arbres qui savent découper.
Target encoding  remplace la modalité par la moyenne de la cible. Très puissant sur
                 forte cardinalité (code postal, produit) — et très exposé à la fuite.
Hashing          projette dans un espace fixe. Utile en streaming, perd l'interprétabilité.
Embeddings       représentation apprise, dense. Pour les réseaux de neurones (module 14).

Le target encoding mérite un mot, car il est à la fois redoutable et dangereux. Pour une modalité \(c\) comptant \(n_c\) observations, on ne prend pas la moyenne brute mais une moyenne lissée vers la moyenne globale :

\[ \tilde{y}_c = \frac{n_c\,\bar{y}_c + m\,\bar{y}}{n_c + m} \]

Le paramètre \(m\) contrôle la régularisation : une modalité vue trois fois est tirée vers la moyenne globale, une modalité vue mille fois garde sa propre moyenne. Surtout, l'encodage doit être calculé en validation croisée interne (chaque pli encodé avec les statistiques des autres plis), faute de quoi chaque ligne contient un peu de sa propre cible — fuite garantie, avec un score de validation flatteur et un modèle inutilisable. sklearn.preprocessing.TargetEncoder fait cela correctement.

Variables numériques et temporelles

  • Transformations — log sur les variables à queue lourde (prix, revenus, durées), Yeo-Johnson si des valeurs négatives ou nulles existent. Cela rend les distributions plus symétriques, ce qui aide les modèles linéaires et les réseaux (pas les arbres, insensibles aux transformations monotones).
  • Discrétisation — transformer l'âge en tranches capture une non-linéarité pour un modèle linéaire, au prix d'une perte d'information.
  • Interactions et ratios — souvent l'apport décisif : prix au m², revenu par personne du foyer, nombre de connexions par jour d'ancienneté. Les arbres approchent mal les ratios, il faut les fournir explicitement.
  • Features temporelles — heure, jour de la semaine, mois, jour férié, ancienneté. Les variables cycliques se codent par \(\sin(2\pi t/T)\) et \(\cos(2\pi t/T)\) pour que 23 h soit proche de 0 h.
  • Agrégats à fenêtre — moyennes, écarts types et comptages sur les 7, 30, 90 derniers jours. C'est le cœur du feature engineering en données transactionnelles, et c'est exactement ce que font les fonctions de fenêtre SQL (module 4). Impérativement calculés avec une fenêtre strictement passée.

Sélection de features

Moins de variables, c'est moins de surapprentissage, moins de coût d'inférence et plus de robustesse. Par ordre de fiabilité croissante : filtres univariés (corrélation, information mutuelle — rapides mais aveugles aux interactions) ; importance par permutation sur un modèle ajusté (module 12) ; élimination récursive (RFE) ; et la régularisation \(L^1\), qui sélectionne en annulant des coefficients. Attention : les méthodes fondées sur la cible doivent, elles aussi, être évaluées à l'intérieur de la validation croisée.

7. Classes déséquilibrées

Fraude à 0,2 %, panne à 1 %, maladie rare : la classe qui intéresse est minuscule. Les réflexes, dans l'ordre de ce qui marche le mieux :

  1. Changer de métrique — l'accuracy n'a aucun sens ici ; PR-AUC, rappel à précision fixée, ou coût métier (module 7).
  2. Pondérer les classes — class_weight="balanced" ou scale_pos_weight : le modèle paie plus cher une erreur sur la classe rare. Simple, sans distorsion des données.
  3. Ajuster le seuil — un modèle produit une probabilité ; le seuil de décision est un choix métier qui se règle sur la courbe précision-rappel, pas à 0,5 par défaut.
  4. Rééchantillonner — sous-échantillonner la majorité (perte d'information) ou sur-échantillonner la minorité (risque de surapprentissage). SMOTE crée des exemples synthétiques par interpolation entre voisins : séduisant, mais il interpole aussi le bruit, fonctionne mal en grande dimension et avec des variables catégorielles, et la littérature récente montre qu'il apporte rarement mieux qu'une simple pondération.
Ne jamais rééchantillonner avant le découpage. Sur-échantillonner puis découper place des copies (ou des interpolations) du même point des deux côtés : le score de validation devient une illusion. Le rééchantillonnage s'applique uniquement au pli d'entraînement — c'est ce que garantit imblearn.pipeline.Pipeline. Et le jeu de test, lui, doit conserver la distribution réelle : c'est celle qu'on rencontrera en production.

8. Validation croisée : choisir le bon schéma

Un découpage unique train/test est bruité : le score dépend du tirage. La validation croisée à \(K\) plis moyenne \(K\) évaluations, chaque observation servant une fois au test. Son écart type entre plis est aussi informatif que la moyenne — un modèle à 0,82 ± 0,01 est préférable à 0,84 ± 0,09.

quel schéma pour quelle structure de données
KFold                  données i.i.d., régression                        K = 5 ou 10
StratifiedKFold        classification : conserve les proportions         le défaut en classif
GroupKFold             plusieurs lignes par entité (patient, client)     un groupe = un seul pli
StratifiedGroupKFold   les deux contraintes à la fois
TimeSeriesSplit        séries temporelles : entraîner sur le passé,      jamais de mélange
                       tester sur le futur (fenêtre glissante)
LeaveOneOut            très peu de données                               coûteux, variance élevée
Nested CV              quand on optimise DES hyperparamètres ET qu'on    boucle interne = réglage
                       veut une estimation non biaisée de performance    boucle externe = évaluation
Python
from sklearn.model_selection import (GroupKFold, StratifiedKFold,
                                     TimeSeriesSplit, cross_validate)

# données transactionnelles : plusieurs lignes par client → GroupKFold
cv = GroupKFold(n_splits=5)
res = cross_validate(pipeline, X, y, groups=df["client_id"],
                     cv=cv, scoring=["roc_auc", "average_precision"],
                     return_train_score=True)

# l'écart train/validation mesure directement le surapprentissage
print(res["train_roc_auc"].mean(), res["test_roc_auc"].mean())

Le protocole que je considère comme correct

  1. Mettre de côté un jeu de test dès le début, et ne l'ouvrir qu'une fois, à la fin.
  2. Travailler en validation croisée sur le reste : exploration, features, réglages.
  3. Optimiser les hyperparamètres dans une boucle interne (nested CV) si l'estimation finale doit être non biaisée.
  4. Réentraîner sur toutes les données d'entraînement avec la configuration retenue.
  5. Évaluer une seule fois sur le test. Si le résultat déçoit et qu'on repart modifier le modèle, ce jeu de test est brûlé : il est devenu un jeu de validation.

9. Fuites de données : le catalogue

La fuite (data leakage) est l'erreur la plus coûteuse de la discipline, parce qu'elle est silencieuse : elle produit d'excellents scores en validation et un modèle qui s'effondre en production. Les formes les plus fréquentes :

formes de fuite
Prétraitement global     scaler, imputeur, PCA, sélection de features ajustés sur TOUT
                         le jeu avant le découpage.        → tout mettre dans un Pipeline

Fuite temporelle         une feature utilise de l'information postérieure à la date de
                         prédiction (moyenne calculée sur toute la période, statut final
                         du dossier).                      → figer une date de référence

Duplication              la même observation (ou quasi) des deux côtés du découpage :
                         doublons, utilisateur présent plusieurs fois.  → GroupKFold

Cible déguisée           une colonne qui n'existe que parce que l'événement a eu lieu :
                         "date de résiliation", "montant remboursé", "motif de panne".

Target encoding naïf     moyenne de cible calculée en incluant la ligne courante.
                         → encodage en validation croisée interne

Fuite par le seuil       choisir le seuil de décision sur le jeu de test.

Sélection répétée        essayer 200 modèles et garder le meilleur score de test :
                         le test devient un jeu d'entraînement déguisé.

Comment la détecter

Un score anormalement élevé (AUC de 0,99 sur un problème réputé difficile) doit déclencher une suspicion, pas une satisfaction. Deux gestes efficaces : regarder les importances de features et se demander, pour la première d'entre elles, si elle serait réellement disponible au moment de la prédiction ; et rejouer la chaîne complète sur une période postérieure (validation temporelle) — une fuite y disparaît, et le score s'effondre. Mieux vaut découvrir cet effondrement en validation qu'en production.

Ce qu'il faut retenir du module

  • Commencer par la décision que le modèle doit éclairer ; définir la cible et une baseline avant toute modélisation.
  • Explorer méthodiquement : structure, cible, manquants, doublons, cardinalités, temps.
  • Comprendre pourquoi une valeur manque avant de l'imputer ; garder l'indicateur de manque.
  • Le feature engineering paie plus que le choix d'algorithme ; ratios, agrégats à fenêtre passée, encodages adaptés à la cardinalité.
  • Déséquilibre : changer de métrique et pondérer avant de songer à SMOTE ; ne rééchantillonner que le pli d'entraînement.
  • Adapter le schéma de validation à la structure des données : groupes, temps, stratification.
  • Tout prétraitement vit dans un pipeline. Un score trop beau est une fuite jusqu'à preuve du contraire.

Data science in practice: from problem to dataset

This module is written in French. The course is my own study material, so it is authored in French only. Switch the language selector to FR to read it; the summary below tells you what it covers.

What this module covers

  • The real shape of a data project, and the one question to answer first: which decision will change because of this model?
  • Framing: defining the target, the observation unit, and a baseline worth beating.
  • An exploration checklist, automated profiling, and the "disguised identifier" trap.
  • Visualisation rules that actually improve readability.
  • Missing data: Rubin's MCAR / MAR / MNAR typology, imputation strategies, and why imputation belongs inside the pipeline.
  • Feature engineering: categorical encodings (including smoothed, cross-fitted target encoding), transformations, cyclical time features, windowed aggregates, feature selection.
  • Imbalanced classes: metrics first, class weights, threshold tuning, and an honest assessment of SMOTE.
  • Cross-validation schemes matched to data structure (groups, time series, stratification), nested CV, and a protocol that keeps the test set honest.
  • A catalogue of data leakage patterns and how to detect them.
