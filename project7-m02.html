Données et déploiement : SQL, NoSQL, Docker, Kubernetes, FastAPI

Un modèle n'existe vraiment que s'il est alimenté par des données stockées quelque part et s'il répond à quelqu'un. Ce module couvre les deux extrémités de la chaîne : d'où viennent les données (SQL, NoSQL, bases vectorielles) et comment le modèle sort du portable (conteneur, orchestration, API).

1. SQL : ce qu'il faut vraiment maîtriser

SQL est déclaratif : on décrit le résultat voulu, le moteur choisit l'algorithme. C'est un changement de posture par rapport à Python, où l'on décrit la marche à suivre. Au-delà du SELECT ... WHERE, quatre constructions couvrent l'essentiel du travail d'analyse.

Jointures

Une jointure associe les lignes de deux tables selon une condition. Les quatre types usuels :

  • INNER JOIN — seulement les lignes appariées des deux côtés ;
  • LEFT JOIN — toutes les lignes de gauche, complétées par NULL à droite si pas d'appariement ;
  • FULL OUTER JOIN — l'union des deux ;
  • CROSS JOIN — le produit cartésien, rarement voulu (et souvent le symptôme d'une condition oubliée).
Le piège n° 1 : l'explosion de cardinalité. Joindre sur une clé qui n'est unique d'aucun côté multiplie les lignes. Une jointure entre 1 000 commandes et 1 000 lignes de facturation partageant le même client_id peut produire un million de lignes — et fausser silencieusement toutes les agrégations qui suivent. Réflexe : vérifier COUNT(*) avant et après chaque jointure.

Agrégations et fonctions de fenêtre

Un GROUP BY écrase les lignes : une ligne par groupe. Une fonction de fenêtre calcule une agrégation sans écraser — chaque ligne conserve son identité tout en voyant son groupe. C'est l'outil décisif pour le feature engineering temporel (module 6), parce qu'il permet de calculer moyennes mobiles, rangs et décalages directement dans la base.

SQL
SELECT
    client_id,
    date_commande,
    montant,
    -- rang de la commande dans l'historique du client
    ROW_NUMBER() OVER (PARTITION BY client_id ORDER BY date_commande) AS n_commande,
    -- montant de la commande précédente : feature de récence
    LAG(montant) OVER (PARTITION BY client_id ORDER BY date_commande) AS montant_precedent,
    -- moyenne glissante sur les 3 dernières commandes, celle-ci incluse
    AVG(montant) OVER (
        PARTITION BY client_id ORDER BY date_commande
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) AS moyenne_3
FROM commandes
WHERE date_commande >= DATE '2025-01-01';

Le ROWS BETWEEN ... AND CURRENT ROW n'est pas cosmétique : il garantit qu'aucune information future n'entre dans la feature. C'est la version SQL de la protection contre la fuite temporelle (module 6).

CTE : structurer une requête

Les Common Table Expressions (WITH) découpent une requête en étapes nommées. Une requête de 80 lignes avec quatre sous-requêtes imbriquées devient quatre blocs lisibles, testables séparément.

SQL
WITH commandes_2025 AS (
    SELECT * FROM commandes WHERE date_commande >= DATE '2025-01-01'
),
agregats_client AS (
    SELECT client_id,
           COUNT(*)                AS n_commandes,
           SUM(montant)            AS ca_total,
           MAX(date_commande)      AS derniere_commande
    FROM commandes_2025
    GROUP BY client_id
)
SELECT c.nom, a.n_commandes, a.ca_total,
       CURRENT_DATE - a.derniere_commande AS jours_depuis_achat
FROM agregats_client a
JOIN clients c USING (client_id)
WHERE a.ca_total > 1000
ORDER BY a.ca_total DESC;

Le piège des NULL

NULL signifie « inconnu », pas « zéro » ni « vide ». Toute comparaison avec NULL vaut NULL (donc faux) : montant != 100 exclut les lignes où montant est NULL, ce qui n'est presque jamais l'intention. De même SUM et AVG ignorent les NULL alors que COUNT(*) les compte : AVG(x) et SUM(x)/COUNT(*) donnent des résultats différents. On teste avec IS NULL, on remplace avec COALESCE(x, 0).

2. Index, plans d'exécution, OLTP vs OLAP

Un index est une structure annexe (le plus souvent un B-tree) qui évite de parcourir toute la table : il transforme un balayage en O(n) en une recherche en O(log n). Le prix : de l'espace disque et un ralentissement des écritures, puisque chaque insertion doit mettre l'index à jour. On indexe les colonnes de jointure, celles des WHERE sélectifs, et celles des ORDER BY fréquents — pas tout le reste.

Pour savoir ce que fait réellement le moteur, on lui demande :

SQL
EXPLAIN ANALYZE
SELECT * FROM commandes WHERE client_id = 42;

-- Seq Scan on commandes  (cost=0.00..18334.00 rows=1 width=44)
--   → balayage complet : 18 000 pages lues pour 1 ligne
-- après CREATE INDEX idx_cmd_client ON commandes(client_id);
-- Index Scan using idx_cmd_client  (cost=0.42..8.44 rows=1 width=44)

Un Seq Scan sur une grande table filtrée finement signale un index manquant. Attention : appliquer une fonction à la colonne (WHERE YEAR(date) = 2025) rend l'index inutilisable — il faut réécrire en WHERE date >= '2025-01-01' AND date < '2026-01-01'.

Deux mondes : transactionnel et analytique

OLTP vs OLAP
                 OLTP (transactionnel)        OLAP (analytique)
Exemples         PostgreSQL, MySQL            DuckDB, ClickHouse, BigQuery, Snowflake
Requêtes         beaucoup, très courtes       peu, très lourdes
Accès            quelques lignes entières     quelques colonnes, millions de lignes
Stockage         par lignes                   par colonnes
Optimisé pour    écriture, cohérence (ACID)   lecture, compression, agrégation
Usage data       la source de vérité          l'analyse et l'entraînement

Le stockage en colonnes est la raison pour laquelle un SELECT AVG(montant) sur 100 millions de lignes est instantané en OLAP : seule la colonne montant est lue, et elle se compresse très bien puisque des valeurs voisines se ressemblent. Pour un usage data science local, DuckDB est le meilleur rapport puissance/simplicité : pas de serveur, il interroge directement des fichiers Parquet ou des DataFrames.

Python
import duckdb

# SQL directement sur des fichiers Parquet, sans import préalable
df = duckdb.sql("""
    SELECT client_id, SUM(montant) AS ca
    FROM 'data/commandes_*.parquet'
    WHERE date_commande >= '2025-01-01'
    GROUP BY client_id
    ORDER BY ca DESC
    LIMIT 10
""").df()                      # renvoie un DataFrame pandas

3. NoSQL : quatre familles, un compromis

NoSQL ne veut pas dire « sans SQL » mais « pas seulement relationnel ». Chaque famille abandonne quelque chose (le plus souvent les jointures et la cohérence forte) pour gagner autre chose (débit, souplesse de schéma, distribution).

familles et usages
Clé-valeur    Redis, DynamoDB     cache, sessions, features en ligne. Accès O(1) par clé.
Document      MongoDB, Firestore  JSON imbriqué, schéma mouvant. Requêtes riches, jointures pauvres.
Colonnes      Cassandra, HBase    écriture massive distribuée, séries temporelles, IoT.
Graphe        Neo4j               relations comme objet premier : fraude, réseaux, recommandation.

Le cadre théorique est le théorème CAP : en cas de partition réseau (P, inévitable dans un système distribué), il faut choisir entre cohérence (C — tout le monde voit la même valeur) et disponibilité (A — le système répond quand même). PostgreSQL privilégie C, Cassandra privilégie A avec une cohérence « à terme ». Pour un projet de data science, la position par défaut raisonnable est : commencer en PostgreSQL, et ne migrer une brique en NoSQL que lorsqu'un besoin précis le justifie (latence de cache, volumétrie d'écriture, schéma réellement instable).

4. Bases vectorielles : premier contact

Une base vectorielle indexe des embeddings — des vecteurs de quelques centaines de dimensions représentant un texte, une image ou un utilisateur — et répond à la question « quels sont les k vecteurs les plus proches de celui-ci ? ». La recherche exacte coûte O(n·d), prohibitive à grande échelle ; on utilise donc des index approchés (ANN) qui échangent un peu de rappel contre un facteur 100 ou 1000 en latence.

Les options : pgvector (extension PostgreSQL — garder une seule base tant que c'est possible), FAISS (bibliothèque locale, sans serveur), Qdrant ou Milvus (services dédiés, filtrage par métadonnées, montée en charge). Le fonctionnement interne des index HNSW et IVF-PQ, ainsi que le pipeline RAG complet, sont traités au module 11.

5. Docker : rendre un projet exécutable ailleurs

Le problème que Docker résout est banal et coûteux : « ça marche chez moi ». Une image est un système de fichiers figé contenant l'application, ses dépendances système et son interpréteur ; un conteneur est une instance en cours d'exécution de cette image, isolée par les namespaces et cgroups du noyau Linux. Contrairement à une machine virtuelle, il n'y a pas de noyau invité : le coût est celui d'un processus ordinaire.

L'image est faite de couches empilées, une par instruction du Dockerfile, mises en cache individuellement. D'où la règle d'or : du plus stable au plus volatil. Les dépendances changent rarement, le code change à chaque commit — les installer avant de copier le code évite de réinstaller tout l'environnement à chaque build.

Dockerfile (projet Python + UV, multi-étapes)
# ── étape 1 : construire l'environnement ──
FROM python:3.12-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv
WORKDIR /app
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy

# dépendances d'abord : cette couche est réutilisée tant que le lock ne bouge pas
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-install-project --no-dev

# puis le code, qui change à chaque commit
COPY src/ src/
RUN uv sync --frozen --no-dev

# ── étape 2 : image finale, sans outils de build ──
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY --from=builder /app/src /app/src
ENV PATH="/app/.venv/bin:$PATH"

RUN useradd -m app && chown -R app /app
USER app                                   # ne jamais tourner en root

EXPOSE 8000
HEALTHCHECK CMD python -c "import urllib.request;urllib.request.urlopen('http://localhost:8000/health')"
CMD ["uvicorn", "mon_projet.api:app", "--host", "0.0.0.0", "--port", "8000"]

La construction en deux étapes (multi-stage) laisse les compilateurs et caches dans l'étape jetable : l'image finale passe typiquement de 1,2 Go à 200 Mo. Un .dockerignore excluant data/, .git/, .venv/ et notebooks/ est indispensable — sans lui, le contexte de build envoie tout le répertoire au démon.

Conteneur et état. Un conteneur est éphémère : tout ce qu'il écrit dans son système de fichiers disparaît à sa destruction. Les données vivent dans des volumes montés, les secrets passent par des variables d'environnement ou un gestionnaire dédié — jamais en dur dans l'image, d'où ils seraient extractibles par quiconque la télécharge.

docker compose décrit une pile complète (API + base + cache) dans un fichier, exactement comme pour la stack Ollama + OpenWebUI de mon projet NAS. Pour le GPU, l'accès passe par le NVIDIA Container Toolkit et l'option --gpus all : le pilote reste sur l'hôte, seules les bibliothèques CUDA sont dans l'image.

6. Kubernetes : ce qu'il faut en savoir

Docker fait tourner des conteneurs sur une machine. Kubernetes (K8s) les fait tourner sur une flotte de machines, en maintenant en permanence l'état réel égal à l'état déclaré. On lui décrit « je veux trois répliques de cette image, avec un GPU chacune », et il s'occupe du placement, des redémarrages, du remplacement des nœuds morts.

objets essentiels
Pod          la plus petite unité déployable : un ou plusieurs conteneurs colocalisés
Deployment   maintient N répliques d'un Pod, gère les mises à jour progressives
Service      une IP et un nom stables devant des Pods éphémères ; répartit la charge
Ingress      l'entrée HTTP depuis l'extérieur (routage, TLS)
ConfigMap    configuration non sensible          Secret   identifiants, clés d'API
Job          tâche ponctuelle (entraînement)     CronJob  tâche récurrente (ré-entraînement)
HPA          autoscaling selon CPU ou métrique personnalisée
deployment.yaml (service d'inférence)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: model-api
spec:
  replicas: 3
  selector:
    matchLabels: { app: model-api }
  template:
    metadata:
      labels: { app: model-api }
    spec:
      containers:
        - name: api
          image: registry.exemple.fr/model-api:1.4.2   # jamais :latest en production
          ports: [{ containerPort: 8000 }]
          resources:
            requests: { cpu: "500m", memory: "1Gi" }   # réservé pour le placement
            limits:   { cpu: "2",    memory: "4Gi",  nvidia.com/gpu: 1 }
          readinessProbe:                              # ne reçoit du trafic qu'une fois le modèle chargé
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 20

Le point non évident pour le ML : requests sert au placement, limits au bridage. Un modèle qui charge 3 Go de poids doit le déclarer, sinon il sera tué (OOMKilled) dès le premier pic. Et la readinessProbe est vitale : sans elle, K8s route du trafic vers un pod dont le modèle n'est pas encore en mémoire.

Kubernetes, en avez-vous besoin ?

Honnêtement, rarement pour un projet personnel ou un prototype : la complexité opérationnelle est réelle. Un conteneur derrière un reverse proxy couvre la grande majorité des besoins. K8s devient pertinent lorsqu'il faut plusieurs machines, de l'autoscaling, des déploiements sans coupure, ou le partage d'un parc de GPU entre plusieurs équipes. La valeur immédiate est de savoir lire un manifeste : c'est la langue commune des équipes plateforme.

7. FastAPI : exposer un modèle

FastAPI combine trois choses utiles : validation des entrées par pydantic (typage vérifié à l'exécution), documentation OpenAPI générée automatiquement, et support natif de l'asynchrone (module 1).

src/mon_projet/api.py
from contextlib import asynccontextmanager
import anyio, joblib, numpy as np
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

etat: dict = {}

@asynccontextmanager
async def lifespan(app: FastAPI):
    # chargé UNE fois au démarrage, pas à chaque requête
    etat["model"] = joblib.load("models/gbm-1.4.2.joblib")
    yield
    etat.clear()

app = FastAPI(title="API de scoring", version="1.4.2", lifespan=lifespan)

class Requete(BaseModel):
    surface: float = Field(gt=0, lt=10_000, description="surface en m²")
    n_pieces: int  = Field(ge=1, le=20)
    code_postal: str = Field(pattern=r"^\d{5}$")

class Reponse(BaseModel):
    prix_estime: float
    version_modele: str

@app.get("/health")                      # sonde de vivacité pour K8s / le load balancer
def health() -> dict:
    return {"status": "ok", "model_loaded": "model" in etat}

@app.post("/predict", response_model=Reponse)
async def predict(req: Requete) -> Reponse:
    X = np.array([[req.surface, req.n_pieces, int(req.code_postal)]])
    try:
        # prédiction = calcul bloquant : on le sort de la boucle d'événements
        y = await anyio.to_thread.run_sync(etat["model"].predict, X)
    except Exception as exc:
        raise HTTPException(status_code=500, detail="échec de l'inférence") from exc
    return Reponse(prix_estime=float(y[0]), version_modele="1.4.2")

Quatre points méritent d'être soulignés, parce qu'ils reviennent systématiquement en production :

  • Charger le modèle au démarrage via lifespan. Le charger dans la fonction de prédiction ajoute des centaines de millisecondes à chaque appel.
  • Sortir le calcul de la boucle d'événements. Un predict scikit-learn est bloquant ; appelé directement dans une coroutine, il gèle tout le serveur pendant son exécution (module 1, section 7.5).
  • Valider strictement les entrées. Les contraintes pydantic rejettent en 422 les valeurs aberrantes avant qu'elles n'atteignent le modèle — première ligne de défense contre les prédictions absurdes sur données hors domaine.
  • Versionner le modèle dans la réponse. Sans cela, impossible de relier a posteriori une prédiction contestée à l'artefact qui l'a produite (module 12).

Pour la montée en charge : uvicorn --workers 4 lance quatre processus (contournant le GIL), chacun chargeant sa copie du modèle — attention à la mémoire. Au-delà, on regroupe les requêtes par lots côté serveur (dynamic batching), ce que font Triton ou vLLM (modules 11 et 12).

Ce qu'il faut retenir du module

  • SQL : jointures maîtrisées (vérifier la cardinalité), fonctions de fenêtre pour les features temporelles, CTE pour la lisibilité, vigilance sur les NULL.
  • Index sur les colonnes de jointure et de filtre ; EXPLAIN ANALYZE pour vérifier plutôt que supposer.
  • OLTP pour la source de vérité, OLAP (DuckDB en local) pour l'analyse.
  • NoSQL seulement quand un besoin précis le justifie ; PostgreSQL couvre beaucoup de cas, y compris vectoriels via pgvector.
  • Docker : couches du stable au volatil, multi-étapes, utilisateur non-root, pas de secret dans l'image.
  • Kubernetes : savoir lire un manifeste et déclarer ses ressources ; ce n'est pas nécessaire pour un prototype.
  • FastAPI : modèle chargé au démarrage, inférence déportée dans un thread, entrées validées, version renvoyée.
