Ugreen DXP6800 Pro - NAS Lab

Le matériel

Le NAS Ugreen DXP6800 Pro est un NAS de la gamme NASync équipé d'un Intel i5-1235U (10 cœurs). J'y ai installé 64 Go de RAM DDR4 et un GPU Nvidia RTX 3050 (6Gb de VRAM) de la marque Yeston en low-profile via le slot PCIe (x4) interne. J'utilise le système d'exploitation fournit par UGREEN : UGOS — un système basé sur Debian 12 (Bookworm).

Ce NAS est ma plateforme d'expérimentation principale : conteneurs Docker, LLM locale, hébergement de services. Les tutos ci-dessous documentent certaines de mes installations.

Tuto 1 — Accès au NAS à distance

Afin d'accéder au NAS à distance, je ne souhaitais pas utiliser le service UGREENlink car il implique une dépendance à un service tiers et le passage des données sur les serveurs de UGREEN. Cela peut ralentir le transit mais également poser question d'un point de vue protection des données. De plus, cela implique une exposition sur Internet du NAS.
J'ai donc opté pour une solution plus classique : acessibilité du NAS uniquement sur mon réseau local. Afin d'accéder au NAS à distance, depuis un autre réseau, j'utilise le système de VPN WireGuard qui est directement hébergé sur ma Freebox. L'hébergement du serveur VPN sur ma box et non sur le NAS permet de protéger le NAS si le VPN est compromis, et d'avoir accès à tous les autres appareils de mon réseau local.

1 Prérequis : demander un adresse IP fixe

Par défaut, l'adresse IP des box internet est attribuée dynamiquement. Elle va donc changer périodiquement. Deux options sont possibles :

  1. Demander une adresse IP fixe dans le panneau de configuration de votre box.
  2. Utiliser un service de DNS dynamique (DDNS) pour mapper un nom de domaine à l'adresse IP du NAS.

L'option 1 est généralement la plus simple à mettre en place.
Pour ma part, je me suis connecté sur mon espace abonné free puis dans "Ma Freebox", j'ai cliqué sur "Demander une adresse IP fixe V4 full-stack".

L'attribution d'une IP fixe peut prendre un certain temps.

2 Activer le serveur VPN sur sa box internet

Pour l'hébergement du serveur VPN sur ma box, je me suis connecté sur le site mafreebox.freebox.fr puis je clique sur "Paramètres de la Freebox" puis sur "Serveur VPN" puis sur "WireGuard" et j'active le service. Ensuite je configure un nouvel utilisateur et je télécharge le fichier de configuration. Il y a également un QR code disponible permettant de configurer rapidement son VPN sur l'application mobile WireGuard.



3 Accéder au NAS

Maintenant il suffit d'activer le VPN sur votre appareil puis accéder au NAS via son adresse IP locale ou via l'application UGREEN NAS.

Tuto 2 — Déployer Ollama + OpenWebUI sur le NAS (stack Docker complète)

Ollama permet de faire tourner des LLM open source en local (sans clé API). Il existe une application pour Windows et Mac OS mais il peut également être lancé via terminal. OpenWebUI offre une interface type ChatGPT afin d'interagir avec les modèles que l'on peut trouver sur Ollama.
Ici, on sera limité dans le choix du modèle à utiliser car il doit pouvoir tourner sur le NAS. Malgré les 64Gb de RAM, les performances sont fortements limitées lorsqu'on exécute sur CPU. Cela est du au fait qu'un CPU est très bon dans l'exécution séquentielle de tâches complexes. Un LLM et autres métamodèles sont essentiellements basés sur la multiplication/inversion de matrices. Des milliards d'opérations sont nécessaires pour chaque token généré. Ces calculs étant parallélisables, faire tourner ces modèles sur GPU permet donc un gain de performance significatif.
Il faut compter envrion 5Gb de VRAM nécessaire pour faire tourner un modèle de 7 milliards de paramètres sur GPU. Avec la configuration actuelle (sans GPU), il faudra se contenter de modèles plus légers.
Un autre tuto est consacré à l'installation d'une carte graphique pour accélérer les performances d'exécution de ces modèles.

Tuto 3 — Corriger les packages UGOS pour accéder au GPU Nvidia dans Docker

J'ai installé une carte graphique Nvidia RTX 3050 sur mon NAS et j'ai installé les pilotes et la toolkit disponibles dans le centre d'application de UGOS.

Si vous souhaitez installer un GPU, il faut vérifier qu'il est compatible (voir la liste des cartes supportées). De plus, si vous souhaitez utiliser le port PCIe 4 pin disponible et intégrer la carte dans le boitier, il faut que la carte soit low-profile, single-slot et quelle consomme moins de 75W. Si vous souhaitez utiliser un GPU plus performant, vous pouvez utiliser le port thunderbolt et fonctionner en eGPU.

Cependant, malgré toutes les précautions, il n'est pas possible, par défaut d'utiliser le GPU via Docker. En effet, le GPU est parfaitement intégré pour les outils d'IA pour le traitement des Photos mais pas pour le reste. Le problème reste néanmoins classique : les drivers Nvidia et CUDA/cuDNN sont installés sur le NAS, mais il manque le NVIDIA Container Toolkit — le composant qui fait le pont entre Docker et les drivers GPU. Sans lui, Docker ne voit pas la carte graphique.

Sur UGOS (Debian 12), une difficulté supplémentaire vient des dépôts locaux CUDA/cuDNN installés par Ugreen qui ont des fichiers Release manquants, bloquant apt.

1 Ouvrir une connexion SSH et tester l'installation

Via l'interface graphique (application UGREEN NAS):

Panneau de configuration → Terminal → SSH → Activer → Appliquer

Puis se connecter depuis PowerShell ou un terminal :

ssh votre_utilisateur@adresse_ip_du_nas

Passer en root :

sudo -i

Tester l'installation du toolkit :

curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey \
  | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg

curl -fsSL https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list \
  | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' \
  | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

sudo apt-get update
sudo apt-get install -y nvidia-container-toolkit

Si vous voyez des erreurs du type "The repository does not have a Release file" pour les dépôts CUDA locaux, passez à l'étape suivante.

2 Désactiver les dépôts CUDA/cuDNN locaux cassés

Les dépôts locaux installés par UGOS pour CUDA 12.8 et cuDNN 9.10.0 ont des fichiers Release manquants. Il faut les désactiver temporairement :

sudo mv /etc/apt/sources.list.d/cuda-debian12-12-8-local.list /tmp/ 2>/dev/null || true
sudo mv /etc/apt/sources.list.d/cudnn-local-repo-debian12-9.10.0.list /tmp/ 2>/dev/null || true
Pourquoi ? Ces dépôts locaux pointent vers des fichiers /var/cuda-repo-*/Release absents. Apt refuse alors de mettre à jour, bloquant toute installation.
3 Réparer les dépendances et installer le toolkit 
# Mettre à jour les listes de paquets
sudo apt-get update

# Corriger les dépendances cassées (libglib2.0, libexiv2, etc.)
sudo apt --fix-broken install -y

# Installer le NVIDIA Container Toolkit
sudo apt-get install -y nvidia-container-toolkit

Cette séquence installe libnvidia-container1, libnvidia-container-tools, nvidia-container-toolkit-base et nvidia-container-toolkit.

4 Configurer Docker et vérifier l'accès GPU

Configurer le runtime NVIDIA pour Docker :

sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

A ce stade, il peut rester un dépôt cuDNN cassé. Ce n'est pas bloquant mais pour retirer l'avertissement :

ls /etc/apt/sources.list.d/ | grep cudnn
  sudo rm /etc/apt/sources.list.d/<nom_du_fichier>

Vérifier que Docker voit bien le GPU :

docker run --rm --gpus all nvidia/cuda:12.0-base nvidia-smi

Si la commande affiche les infos de votre carte Nvidia, tout est en ordre. Vous pouvez maintenant relancer la stack Ollama avec accélération GPU.

Tuto 5 — Faire tourner un modèle de 35B sur 6 Go de VRAM (MoE, Ollama vs llama.cpp)

Avec 6 Go de VRAM, un petit modèle dense comme qwen3.5:4b tient entièrement sur la carte et répond vite (environ 39 tokens/s), mais ses capacités restent limitées. Pour aller plus loin sans changer de GPU, je me suis tourné vers un modèle MoE (Mixture of Experts) : Qwen3.6 35B-A3B. Il compte 35 milliards de paramètres au total, mais n'en active qu'environ 3 milliards pour chaque token généré.

En quantification Q4, le modèle pèse environ 21 Go : il ne tient pas dans la VRAM et se répartit entre le GPU et les 64 Go de RAM du NAS. Pour un modèle dense, ce serait rédhibitoire : tous les paramètres sont relus à chaque token et la RAM devient le goulot d'étranglement. Un MoE ne lit que les experts actifs, ce qui garde une vitesse correcte même quand la majorité du modèle est en RAM.

1 Premier essai avec Ollama

Le plus simple est de passer par la stack du tuto 2 :

docker exec -it ollama ollama pull qwen3.6:35b-a3b-q4_K_M

Premiers résultats, mesurés dans Open WebUI : environ 14 tokens/s en génération, ce qui est tout à fait utilisable, mais seulement 158 tokens/s pour la lecture du prompt et 65 secondes de chargement au premier message. La lecture du prompt est le vrai point faible : dès que l'on donne un long fichier ou un long historique, l'attente avant le premier mot devient importante.

La RAM « Cache » dans UGOS : après le chargement, le moniteur de ressources affichait 50 Go en « Cache » et seulement 5 Go « Restant ». Pas d'inquiétude : c'est le cache disque de Linux (ici, en grande partie le fichier du modèle), libéré dès qu'un programme en a besoin. La colonne available de free -h donne la mémoire réellement disponible.
2 Déployer llama.cpp (llama-server) avec Docker

llama.cpp est le moteur sur lequel repose Ollama. Utilisé directement, il donne accès à des réglages qu'Ollama ne propose pas, en particulier --n-cpu-moe : on place tout le modèle sur le GPU, puis on renvoie en RAM uniquement les experts d'un certain nombre de couches. L'attention et le cache de contexte restent sur la carte, et ce sont justement eux qui servent à lire le prompt.

mkdir -p /volume1/docker/llama-cpp/models
cd /volume1/docker/llama-cpp
vim docker-compose.yml
docker-compose.yml
services:
  llama-server:
    image: ghcr.io/ggml-org/llama.cpp:server-cuda
    container_name: llama-server
    ports:
      - "8080:8080"
    volumes:
      - ./models:/root/.cache/huggingface
    command: >
      -hf unsloth/Qwen3.6-35B-A3B-GGUF:UD-Q4_K_XL
      --host 0.0.0.0 --port 8080
      --load-mode none
      --no-mmproj -np 1
      -ngl 99 --n-cpu-moe 36
      -b 2048 -ub 2048
      -t 6
      -c 32768 --jinja
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
    restart: unless-stopped

Les options :

  • -hf : télécharge le modèle depuis Hugging Face au premier démarrage (environ 21 Go), dans le dossier ./models monté sur /root/.cache/huggingface.
  • --load-mode none : copie réellement les experts en RAM au lieu de lire le fichier à travers le cache disque. C'est llama.cpp lui-même qui le recommande dans ses logs.
  • --no-mmproj : ne charge pas l'encodeur d'images du modèle, qui réclamait 861 Mo de VRAM que la carte n'avait plus.
  • -np 1 : une seule requête traitée à la fois (voir l'étape 5).
  • -ngl 99 --n-cpu-moe 36 : tout le modèle sur le GPU, sauf les experts de 36 couches, renvoyés en RAM.
  • -b 2048 -ub 2048 : lit le prompt par paquets de 2 048 tokens. Les experts stockés en RAM doivent être transférés vers le GPU à chaque paquet, et le slot PCIe 4.0 x4 du NAS plafonne à environ 8 Go/s : des paquets plus gros signifient moins de transferts. Avec ce réglage, la lecture du prompt est passée de 132 à 343 tokens/s.
  • -t 6 : 6 threads CPU (voir l'étape 3).
  • -c 32768 --jinja : contexte de 32K tokens, et format de conversation propre au modèle.
docker compose up -d
docker logs -f llama-server

Le serveur est prêt quand les logs affichent listening on http://0.0.0.0:8080.

3 Trouver les bons réglages avec llama-bench

L'i5-1235U compte 2 cœurs performants et 8 cœurs économes : le bon nombre de threads ne se devine pas. llama.cpp fournit un outil de benchmark, inclus dans l'image full-cuda, qui teste toutes les combinaisons d'un coup. Il faut d'abord arrêter llama-server pour libérer la VRAM :

docker compose stop
docker run --rm --gpus all \
  -v /volume1/docker/llama-cpp/models:/root/.cache/huggingface \
  ghcr.io/ggml-org/llama.cpp:full-cuda --bench \
  -m /root/.cache/huggingface/hub/models--unsloth--Qwen3.6-35B-A3B-GGUF/snapshots/<hash>/Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf \
  -ngl 99 -ncmoe 36,38 -t 4,6,8,10 -p 512 -n 128

Résultats sur mon NAS (pp512 : lecture d'un prompt de 512 tokens ; tg128 : génération de 128 tokens) :

n_cpu_moe  threads  pp512 (tok/s)  tg128 (tok/s)
       36        4          202,8           13,7
       36        6          201,3           15,8
       36        8          197,4           15,8
       36       10          198,6           14,7
       38        4          193,3           13,2
       38        6          191,1           15,2
       38        8          193,5           15,1
       38       10          192,4           14,1

Au-delà de 8 threads, les cœurs économes ralentissent l'ensemble. 6 threads donnent la même vitesse que 8 en chargeant moins le CPU. Passer de 38 à 36 couches d'experts en RAM ne rapporte que 0,6 token/s, et descendre plus bas fait déborder la VRAM. Le meilleur réglage est donc --n-cpu-moe 36 -t 6.

4 Les pièges rencontrés
  • Manque de VRAM au démarrage (cudaMalloc failed: out of memory) : avec --n-cpu-moe 32, les poids seuls occupaient déjà 5,85 Go. Il faut laisser de la place au cache de contexte et aux buffers de calcul, qui grossissent avec -ub 2048.
  • Le réglage automatique désactivé : la ligne failed to fit params ... n_gpu_layers already set by user indique que llama.cpp sait répartir le modèle seul, mais uniquement si l'on ne fixe pas -ngl. Dans mon cas, les valeurs trouvées au benchmark ont donné de meilleurs résultats que ce réglage automatique.
  • L'encodeur d'images : Qwen3.6 est multimodal, et -hf charge aussi sa partie vision, d'où un nouveau manque de VRAM. Solution : --no-mmproj, ou --no-mmproj-offload pour la garder sur le CPU.
  • Le mauvais dossier de cache : le modèle se télécharge dans /root/.cache/huggingface. Avec un volume monté ailleurs, les 21 Go restent à l'intérieur du conteneur et sont retéléchargés à chaque recréation. Pour récupérer un modèle déjà téléchargé : docker cp llama-server:/root/.cache/huggingface/. ./models/.
  • Un seul moteur à la fois sur le GPU : une fois llama-server chargé, la VRAM est pleine à 98 % et Ollama ne peut plus charger de modèle (erreur de mémoire). Il faut arrêter l'un pour utiliser l'autre.
5 Brancher llama-server dans Open WebUI et alléger les requêtes

llama-server expose une API compatible OpenAI. Dans Open WebUI : Panneau d'administration → Paramètres → Connexions → API OpenAI, ajouter l'URL http://<ip_nas>:8080/v1 avec une clé quelconque (par exemple none). Le modèle apparaît alors dans la liste, à côté de ceux d'Ollama.

Lors des premiers tests, une question d'une ligne envoyait pourtant plus de 7 000 tokens de prompt : les outils intégrés d'Open WebUI (notes, saisie utilisateur, affichage de fichiers…) ajoutent leurs descriptions à chaque requête, et le modèle s'en servait sans raison, avec des appels ratés. J'ai donc créé un modèle personnalisé réservé à la discussion (Espace de travail → Modèles) :

  • Outils intégrés : désactivés ;
  • Vision : désactivée, puisque le serveur tourne sans encodeur d'images ;
  • Interpréteur de code : désactivé, car il n'exécute que du Python et ajoute des instructions au prompt ;
  • Fichier dans le contexte : activé, pour que le modèle lise en entier les fichiers qu'on lui envoie.

Résultat : le prompt d'une question simple est passé de plus de 7 000 tokens à une trentaine.

Deuxième levier, le mode réflexion. Pour « la suite de Fibonacci en Rust avec un graphique », le modèle générait 5 555 tokens, soit 7 minutes, dont l'essentiel en réflexion. Dans Model controls, j'ai ajouté un menu « Thinking » avec deux options, Off par défaut :

Option   Paramètre               Valeur
On       chat_template_kwargs    {"enable_thinking": true}
Off      chat_template_kwargs    {"enable_thinking": false}

Pour un modèle servi par Ollama, le paramètre s'appelle think (valeurs true / false). Sans réflexion, une réponse équivalente tient en 1 300 à 1 800 tokens, soit environ 2 minutes.

Enfin, pourquoi -np 1 : avec 4 slots, le serveur traitait en parallèle la réponse en cours et les requêtes de fond d'Open WebUI (génération du titre, des tags), qui se partageaient la bande passante de la RAM. La génération tombait à 9,3 tokens/s ; avec un seul slot, elle remonte à 15,4.

6 Bilan : Ollama ou llama.cpp ? 
                               Ollama (départ)    llama.cpp (final)
Génération                     14 tok/s           15,4 tok/s
Lecture d'un long prompt       158 tok/s          343 tok/s
Prompt d'une question simple   ~2 000 tokens      ~30 tokens
Réflexion                      toujours active    au choix

En appliquant les mêmes réglages côté Ollama (outils désactivés, think à false, contexte de 32K, 6 threads), j'obtiens 14,5 tokens/s : sur une question courte, l'essentiel du gain vient donc de la configuration d'Open WebUI, pas du moteur. L'avantage net de llama.cpp, c'est une lecture du prompt deux fois plus rapide, qui compte dès que l'on donne des fichiers à lire ou que l'on utilise un agent. Ollama reste plus simple et permet de changer de modèle en un clic.

Dernier point utile, le cache de prompt : au deuxième message d'une conversation, llama-server a réutilisé 1 848 tokens sur 1 891 et n'a lu que les nouveaux. La réponse a démarré en 1,3 seconde.

Tuto 6 — Un agent IA sur le NAS, piloté depuis Telegram (OpenClaw)

OpenClaw est un agent IA auto-hébergé. Contrairement à Open WebUI, qui se contente de discuter, il peut agir : lire et écrire des fichiers, exécuter des commandes, planifier des tâches. On lui parle depuis une messagerie (Telegram, Discord, Slack, WhatsApp). C'est un peu un Claude Code que l'on pilote depuis son téléphone, sans avoir à se connecter au VPN.

OpenClaw n'est pas un moteur : c'est un harness, le programme qui entoure le modèle et le fait tourner en boucle avec des outils. Il faut lui fournir un LLM, ici le Qwen3.6 35B-A3B du tuto 5, servi par Ollama.

En contrepartie, les messages transitent par les serveurs de Telegram, et les conversations avec un bot ne sont pas chiffrées de bout en bout : je n'y envoie rien de sensible. Pour accéder à Open WebUI à distance, je continue d'utiliser le VPN du tuto 1.

Sécurité. Un agent qui lit des messages et peut exécuter des commandes sur le NAS est une cible idéale pour l'injection de prompt : un fichier ou un message piégé peut lui faire faire autre chose que ce qui était demandé. Je ne lui donne accès qu'à deux dossiers dédiés, le bot ne répond qu'à mon compte, et je n'installe aucune extension (skill) tierce sans l'avoir lue.
1 Préparer Ollama pour un agent

Arrêter d'abord llama-server (tuto 5) pour libérer la VRAM :

docker stop llama-server

Un agent envoie de très gros prompts : instructions, descriptions d'outils, historique. Ollama utilise par défaut un contexte court, et tronque le prompt sans prévenir quand il le dépasse. On crée donc une variante du modèle avec ses propres réglages :

docker exec -it ollama sh -c 'printf "FROM qwen3.6:35b-a3b-q4_K_M\nPARAMETER num_ctx 32768\nPARAMETER num_thread 6\nPARAMETER temperature 0.6\nPARAMETER presence_penalty 0\n" > /tmp/Modelfile && ollama create qwen3.6-agent -f /tmp/Modelfile'

docker exec ollama ollama show qwen3.6-agent --parameters
  • num_ctx 32768 : contexte de 32K tokens ;
  • num_thread 6 : le meilleur réglage trouvé au tuto 5 ;
  • temperature 0.6 et presence_penalty 0 : les réglages recommandés par Qwen pour le code. Une pénalité de présence pousse le modèle à éviter les répétitions, ce qui le gêne quand il doit réutiliser les mêmes noms de variables.
Pourquoi ne pas le faire dans Open WebUI ? Les modèles personnalisés d'Open WebUI n'existent que dans Open WebUI, qui ajoute leurs réglages aux requêtes qu'il envoie. OpenClaw s'adresse directement à Ollama : la variante doit donc exister dans Ollama.

Ensuite, dans le docker-compose.yml du tuto 2, ajouter deux variables d'environnement au service ollama :

    environment:
      - OLLAMA_HOST=0.0.0.0
      - OLLAMA_ORIGINS=*
      - OLLAMA_KEEP_ALIVE=-1
      - OLLAMA_NUM_PARALLEL=1
  • OLLAMA_KEEP_ALIVE=-1 : le modèle reste chargé en mémoire. Sinon, chaque tâche commence par une minute de chargement ;
  • OLLAMA_NUM_PARALLEL=1 : une requête à la fois, l'équivalent de -np 1 dans llama.cpp.
cd /volume1/docker/ai-stack
docker compose up -d
docker exec ollama env | grep OLLAMA
curl http://<ip_nas>:11434/api/tags

OpenClaw tourne dans son propre conteneur : pour lui, localhost désigne ce conteneur et non le NAS. Il faut donc passer par l'adresse IP locale du NAS, et vérifier que qwen3.6-agent apparaît bien dans la réponse de curl.

2 Installer OpenClaw depuis le centre d'applications UGOS

OpenClaw est disponible dans le centre d'applications d'UGOS (l'installation prend une dizaine de minutes). Avant de la lancer, créer deux dossiers vides, /volume1/docker/openclaw/workspace et /volume1/docker/openclaw/share. L'assistant d'installation demande trois choses :

  • Chemin de l'espace de travail : openclaw/workspace, monté dans le conteneur sur /root/.openclaw/workspace. C'est le dossier de l'agent : il y écrit son code, ses fichiers temporaires et ses fichiers de mémoire.
  • Chemin d'accès au fichier : openclaw/share, monté dans le conteneur au même chemin que sur le NAS (/volume1/docker/openclaw/share). C'est le seul dossier existant qu'il peut lire et modifier. Je n'y dépose que les fichiers sur lesquels je veux le faire travailler, et surtout pas mes Documents ou mes Médias. Ce dossier ne doit pas se trouver dans l'espace de travail.
  • Jeton de passerelle : le mot de passe de l'interface web d'OpenClaw. Le générer avec openssl rand -hex 32 et le conserver dans un gestionnaire de mots de passe.

Une fois l'installation terminée, Ugreen fournit une console d'administration (Overview, Model Providers, Channels, Logs) dans laquelle se fait toute la configuration.

3 Brancher le modèle (Model Providers)

Dans Model Providers → Add provider, choisir Ollama, puis :

  • Base URL : http://<ip_nas>:11434, et non localhost ;
  • API protocol : Ollama ;
  • API Key : ollama. Ollama n'en a pas besoin mais le champ est obligatoire. Attention, le navigateur peut le préremplir avec un mot de passe enregistré ;
  • Model list : supprimer les modèles d'exemple (llama3.1, qwen2.5) et ajouter qwen3.6-agent.

Pour le modèle :

  • Context window : 32768. Avec le protocole Ollama, OpenClaw peut transmettre cette valeur à chaque requête : la laisser à 131 072, comme dans les exemples, écraserait le réglage de la variante ;
  • Max output tokens : 8192, pour que les réponses avec réflexion ne soient pas coupées ;
  • Reasoning model : coché, puisque Qwen3.6 réfléchit avant de répondre ;
  • Coûts : 0, le modèle tourne en local.
4 Créer le bot Telegram et l'appairer

J'ai choisi Telegram : le bot est un compte séparé, créé en deux minutes, qui passe par l'API officielle sans lier son propre compte. Avec WhatsApp, au contraire, OpenClaw se connecte comme appareil lié à votre propre compte, par une méthode non officielle.

  1. Créer un compte Telegram si besoin. Dans Paramètres → Confidentialité et sécurité → Numéro de téléphone, je conseille de choisir « Personne » pour la visibilité du numéro.
  2. Ouvrir @BotFather (celui qui porte le badge bleu de vérification), envoyer /newbot, choisir un nom d'affichage, puis un nom d'utilisateur se terminant par bot. BotFather renvoie un jeton (7123456789:AAH…) à garder secret ; en cas de fuite, /revoke en génère un nouveau.
  3. Dans la console OpenClaw, Channels : activer le plugin Telegram, puis Add channel, coller le jeton et garder DM Policy sur pairing.
  4. Envoyer un premier message au bot : il répond avec un code d'appairage et ignore tout le reste tant que ce code n'a pas été approuvé.
docker ps --format '{{.Names}}' | grep -i claw
docker exec -it openclaw-gateway-1 openclaw pairing approve telegram <CODE>

Avec le mode pairing, personne ne peut donner d'ordres au bot sans mon accord, même en connaissant son nom. Ne jamais choisir open.

5 Les erreurs rencontrées

« No API key found for provider "openai" » : le fournisseur Ollama était bien ajouté, mais l'agent utilisait toujours OpenAI par défaut.

docker exec -it openclaw-gateway-1 openclaw models list
docker exec -it openclaw-gateway-1 openclaw models set ollama/qwen3.6-agent
docker restart openclaw-gateway-1

« Request timed out before a response was generated », systématiquement au bout d'une minute. Les logs d'Ollama donnent l'explication : le prompt système d'OpenClaw, avec les descriptions de ses outils, fait environ 13 000 tokens. À environ 150 tokens/s, il faut près de 85 secondes au modèle pour le lire avant d'écrire le premier mot.

Le délai suggéré par le message d'erreur (agents.defaults.timeoutSeconds) ne suffit pas : la version installée par UGOS (2026.3.31) a un second délai, de 60 secondes par défaut, pour l'attente du premier token. Il faut augmenter les deux :

docker exec -it openclaw-gateway-1 openclaw config set agents.defaults.timeoutSeconds 600
docker exec -it openclaw-gateway-1 openclaw config set agents.defaults.llm.idleTimeoutSeconds 600
docker restart openclaw-gateway-1
Astuce : pendant les tests, envoyer un seul message et attendre. Avec une requête à la fois, chaque nouveau message s'ajoute à la file d'attente. Pour éviter la minute de chargement, on peut aussi précharger le modèle :
curl http://<ip_nas>:11434/api/generate -d '{"model":"qwen3.6-agent","keep_alive":-1}'

« Exec approval is required, but no interactive approval client is currently available », puis « Je ne trouve pas le fichier ». J'avais demandé de résumer un fichier déposé dans le dossier partagé, mais l'agent ne savait pas où ce dossier était monté : il a tenté un find sur tout /root. Les commandes shell exigent une approbation, et aucun moyen d'approuver n'étant configuré, la demande a expiré et la commande a été refusée. C'est le comportement attendu : ce garde-fou empêche l'agent de fouiller le système.

La solution est de lui donner le chemin exact. Pour voir où chaque dossier est monté dans le conteneur :

docker inspect openclaw-gateway-1 --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
/volume1/docker/openclaw/workspace -> /root/.openclaw/workspace
/volume1/docker/openclaw/share -> /volume1/docker/openclaw/share

Puis on l'indique à l'agent, une fois pour toutes :

Le dossier partagé est /volume1/docker/openclaw/share. Note ce chemin dans tes fichiers de mémoire.

Avec le chemin exact, il lit les fichiers avec son outil de lecture, sans passer par le shell, donc sans demande d'approbation. Pour autoriser malgré tout certaines commandes shell, avec une confirmation à chaque fois, voir l'étape 7 (et la documentation des approbations).

6 Premier contact : identité et règles de l'agent

Au premier message, OpenClaw lance une étape d'accueil : il demande son nom, sa nature, son style et un emoji, puis enregistre le tout dans des fichiers Markdown de son espace de travail (IDENTITY.md, USER.md, SOUL.md…). Ces fichiers lui servent de mémoire : il les relit à chaque session. J'ai répondu en un seul message pour limiter les allers-retours :

Appelle-toi Atlas, assistant technique pour mon NAS, spécialiste en IT/IA/LLM/Tech, style direct et concis, emoji 🛰️

Puis j'ai fixé ses règles de comportement, qu'il a enregistrées dans SOUL.md :

- Réponses courtes et directes, en français.
- Pas de tableaux Markdown, Telegram ne les affiche pas : utilise des listes.
- Demande-moi toujours confirmation avant de supprimer un fichier
  ou d'exécuter une commande qui modifie le système.
- Ne travaille que dans ton espace de travail et dans le dossier partagé.

Deux remarques :

  • L'agent a annoncé « C'est fait » alors qu'une de ses modifications de SOUL.md avait échoué. Les modèles de cette taille affirment souvent avoir réussi une action ratée : il faut vérifier le fichier soi-même (ici, tout y était).
  • Ces règles aident, mais ne constituent pas une vraie protection : l'agent peut réécrire ses propres fichiers. Si on lui donne un jour accès à des contenus extérieurs (pages web, mails), on peut protéger le fichier en écriture : chmod 444 <chemin>/openclaw/workspace/SOUL.md.

À la fin de l'accueil, il propose de supprimer BOOTSTRAP.md, qui ne sert plus. Bon signe : il a demandé confirmation avant de le faire.

7 Autoriser les commandes shell, avec confirmation dans Telegram

Par défaut, chaque commande shell doit être approuvée, mais aucun moyen d'approuver n'est configuré : les commandes expirent et sont refusées. On peut se désigner comme approbateur : chaque commande arrive alors dans Telegram, en clair, avec des boutons pour l'autoriser ou la refuser. L'approbateur se désigne par son identifiant Telegram numérique (celui affiché par la commande d'appairage, « Approved telegram sender … ») : avoir le droit d'écrire au bot ne suffit pas.

Sauvegarder d'abord la configuration (le dossier /root/.openclaw du conteneur correspond à ce dossier du NAS) :

cp /volume1/@appstore/com.ugreen.docker.openclaw/config/openclaw.json \
   /volume1/@appstore/com.ugreen.docker.openclaw/config/openclaw.json.bak

Puis activer les approbations, en remplaçant TON_ID par son identifiant Telegram :

docker exec -it openclaw-gateway-1 openclaw config set channels.telegram.execApprovals.enabled true
docker exec -it openclaw-gateway-1 openclaw config set channels.telegram.execApprovals.approvers '[TON_ID]'
docker exec -it openclaw-gateway-1 openclaw config set channels.telegram.capabilities.inlineButtons dm

docker exec -it openclaw-gateway-1 openclaw config get channels.telegram
docker restart openclaw-gateway-1
  • execApprovals.approvers : la liste des approbateurs. Dans le résultat de config get, elle doit apparaître comme une liste contenant un nombre, et non comme un texte entre guillemets ;
  • capabilities.inlineButtons dm : autorise les boutons dans les messages privés, indispensables pour approuver d'un simple appui.

Pour tester, je demande à Atlas : « Exécute ls -la /volume1/docker/openclaw/share ». Le bot répond avec un message « Approval required » qui affiche la commande, le dossier dans lequel elle s'exécutera et le délai d'expiration (30 minutes), suivi de trois boutons :

  • Allow Once : autorise cette commande une seule fois. C'est le choix par défaut ;
  • Allow Always : ajoute la commande à une liste d'autorisations permanentes, que l'agent pourra relancer sans demander. Je le réserve aux commandes en lecture seule que je vois passer souvent, jamais à une commande qui supprime, déplace ou télécharge quelque chose ;
  • Deny : refuse la commande.

Les mêmes choix existent sous forme de commandes à taper (/approve <id> allow-once, allow-always ou deny). Répondre simplement « oui » dans la conversation ne compte pas comme une approbation.

À savoir : la ligne « Host: gateway » indique que les commandes s'exécutent dans le conteneur d'OpenClaw, en root, et non directement sur le système du NAS. Elles n'atteignent que les dossiers montés dans ce conteneur. C'est une protection de plus, mais pas une garantie absolue : la vraie sécurité reste de lire chaque commande avant de l'approuver, et de refuser tout ce qui sort de workspace et share.
8 Couper l'accès à Internet de l'agent

Le modèle lui-même n'a jamais accès à Internet : Ollama se contente de produire du texte. Ce qui peut sortir sur Internet, c'est OpenClaw, à travers ses outils. Les logs le montrent dès les premiers échanges : web_search: no provider configured ... falling back to keyless provider "duckduckgo". La recherche web est active par défaut, sans clé, via DuckDuckGo. Or une page web est la source la plus probable d'injection de prompt.

Trois portes mènent à Internet :

  • web_search et web_fetch (groupe group:web) : chercher et lire des pages web ;
  • browser (groupe group:ui) : un navigateur piloté par l'agent ;
  • les commandes shell comme curl ou wget, déjà soumises à approbation depuis l'étape 7.

On ne peut pas couper le réseau du conteneur lui-même : OpenClaw en a besoin pour parler à Telegram. On interdit donc les outils, après avoir sauvegardé la configuration :

docker exec -it openclaw-gateway-1 openclaw config set tools.deny '["group:web","browser"]'
docker exec -it openclaw-gateway-1 openclaw config set tools.web.search.enabled false
docker exec -it openclaw-gateway-1 openclaw config set tools.web.fetch.enabled false
docker restart openclaw-gateway-1

docker exec -it openclaw-gateway-1 openclaw config get tools

L'interdiction (tools.deny) l'emporte sur toute autorisation. Je vérifie avec config get après le redémarrage, car le gestionnaire d'Ugreen réécrit une partie de la configuration à chaque démarrage (Syncing configuration from environment variables... dans les logs).

Pour tester, je demande à Atlas : « Recherche sur le web la dernière version d'Ollama ». Il n'a plus d'outil web… et tente aussitôt de contourner avec une commande shell :

curl -s https://api.github.com/repos/ollama/ollama/releases/latest | grep -o '"tag_name": *"[^"]*"' | head -1

C'est l'approbation de l'étape 7 qui l'arrête : je refuse avec Deny, sans jamais utiliser Allow Always pour curl ou wget. Pour qu'il cesse d'essayer, j'ai ajouté cette règle directement dans SOUL.md :

- Tu n'as pas accès à Internet. N'utilise jamais curl, wget ou tout autre moyen
  de contacter un site externe. Si une information nécessite Internet, dis-le-moi.

Au final, trois niveaux de protection : les outils web désactivés, une consigne qui incite l'agent à ne plus essayer (qu'il peut ne pas respecter), et l'approbation de chaque commande shell, qui reste la vraie barrière. Interdire un outil ne suffit pas tant que le shell est disponible. Bonus : chaque outil retiré enlève sa description du prompt système, ce qui accélère un peu les réponses.

Attention aux logs : au démarrage, les logs du conteneur affichent un jeton en clair (--token …). Il faut le masquer avant de partager des logs. Si c'est le jeton de passerelle choisi à l'installation, UGOS ne permet de le changer qu'en réinitialisant l'application : il faut alors refaire la configuration de ce tuto (les dossiers workspace et share, et donc la mémoire de l'agent, sont conservés).
9 Performances et pistes d'amélioration

Sur cette configuration, la première réponse arrive en un peu plus d'une minute, et une tâche avec plusieurs appels d'outils (écrire des fichiers puis répondre) prend environ 4 minutes. C'est nettement plus lent qu'Open WebUI, pour deux raisons : le prompt passe d'une trentaine de tokens à environ 13 000, et chaque appel d'outil relance le modèle. L'usage est donc plutôt asynchrone : on envoie une demande depuis Telegram et on revient voir le résultat plus tard.

Pistes pour accélérer :

  1. Brancher OpenClaw sur llama-server (tuto 5) plutôt que sur Ollama : la lecture du prompt y est deux fois plus rapide, et c'est exactement ce qui limite un agent.
  2. Vérifier que le cache de prompt fonctionne d'un tour à l'autre (docker logs ollama | grep cached). Si tout le prompt est relu à chaque tour, c'est ce qui coûte le plus cher.
  3. Réduire encore le prompt système en désactivant les autres outils inutiles (les outils web le sont déjà depuis l'étape 8).
  4. Désactiver la réflexion, au prix d'actions moins fiables.

Pour comprendre plus en détail le fonctionnement d'un agent (boucle, outils, contexte, sécurité), voir le projet 8, dans lequel je construis un agent de code à la main.

Tuto 1 — Remote Access to the NAS

In order to access the NAS remotely, I did not want to use the UGREENlink service because it involves a dependency on a third-party service and the transfer of data through UGREEN's servers. In order to access the NAS remotely, from another network, I use the WireGuard VPN system which is directly hosted on my Freebox. 1 Requirements : Request a static IP address

By default, the IP address of internet boxes is assigned dynamically. It will therefore change periodically. Two options are possible :

  1. Request a static IP address in the configuration panel of your box.
  2. Use a dynamic DNS (DDNS) service to map a domain name to the NAS's IP address.

Option 1 is generally the simplest to set up.
For my part, I logged into my free subscriber area and then in "My Freebox", I clicked on "Request a static IPv4 full-stack address".

For hosting the VPN server on my box, I logged into the website mafreebox.freebox.fr then clicked on "Box Settings" then on "VPN Server" then on "WireGuard" and activated the service. Tuto 2 — Deploy Ollama + OpenWebUI on the NAS (Complete Docker Stack)

Ollama allows you to run open-source LLMs locally (without an API key). There is an application for Windows and Mac OS, but it can also be run via the terminal. OpenWebUI provides a ChatGPT-style interface to interact with the models available on Ollama.
Here, we will be limited in the choice of models to use as they must be able to run on the NAS. Despite having 64GB of RAM, performance is significantly limited when running on CPU. This is because a CPU is very good at executing sequential tasks. LLMs and other meta-models are essentially based on matrix multiplication/inversion. Billions of operations are needed for each generated token. Since these calculations are parallelizable, running these models on GPU allows for a significant performance gain.
You need to account for approximately 5GB of VRAM necessary to run a 7-billion-parameter model on GPU. With the current configuration (without GPU), you will have to settle for lighter models.
Another tutorial is dedicated to installing a graphics card to accelerate the performance of these models.

It is possible to use the Docker application available in UGOS, but I prefer to use the SSH terminal for more flexibility:

Configuration Panel → Terminal → SSH → Enable → Apply

sudo -i

Tuto 5 — Running a 35B model on 6 GB of VRAM (MoE, Ollama vs llama.cpp)

With 6 GB of VRAM, a small dense model such as qwen3.5:4b fits entirely on the card and answers quickly (about 39 tokens/s), but its capabilities remain limited. To go further without changing GPU, I turned to an MoE (Mixture of Experts) model: Qwen3.6 35B-A3B. It has 35 billion parameters in total, but only activates about 3 billion for each generated token.

With Q4 quantization, the model weighs about 21 GB: it does not fit in VRAM and is split between the GPU and the NAS's 64 GB of RAM. For a dense model this would be a deal-breaker, since every parameter is read again for each token and RAM becomes the bottleneck. An MoE only reads the active experts, which keeps a decent speed even when most of the model sits in RAM.

1 First attempt with Ollama

The simplest option is to use the stack from tutorial 2:

docker exec -it ollama ollama pull qwen3.6:35b-a3b-q4_K_M

First results, measured in Open WebUI: about 14 tokens/s for generation, which is perfectly usable, but only 158 tokens/s for prompt reading and 65 seconds of loading on the first message. Prompt reading is the real weak point: as soon as you provide a long file or a long history, the wait before the first word becomes significant.

"Cache" RAM in UGOS: after loading, the resource monitor showed 50 GB as "Cache" and only 5 GB "Remaining". No need to worry: this is the Linux disk cache (here, mostly the model file), released as soon as a program needs it. The available column of free -h gives the memory that is actually available.
2 Deploy llama.cpp (llama-server) with Docker

llama.cpp is the engine Ollama is built on. Used directly, it gives access to settings Ollama does not offer, in particular --n-cpu-moe: the whole model is placed on the GPU, then only the experts of a given number of layers are sent back to RAM. Attention and the context cache stay on the card, and they are precisely what is used to read the prompt.

mkdir -p /volume1/docker/llama-cpp/models
cd /volume1/docker/llama-cpp
vim docker-compose.yml
docker-compose.yml
services:
  llama-server:
    image: ghcr.io/ggml-org/llama.cpp:server-cuda
    container_name: llama-server
    ports:
      - "8080:8080"
    volumes:
      - ./models:/root/.cache/huggingface
    command: >
      -hf unsloth/Qwen3.6-35B-A3B-GGUF:UD-Q4_K_XL
      --host 0.0.0.0 --port 8080
      --load-mode none
      --no-mmproj -np 1
      -ngl 99 --n-cpu-moe 36
      -b 2048 -ub 2048
      -t 6
      -c 32768 --jinja
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
    restart: unless-stopped

The options:

  • -hf: downloads the model from Hugging Face on first start (about 21 GB), into the ./models folder mounted on /root/.cache/huggingface.
  • --load-mode none: actually copies the experts into RAM instead of reading the file through the disk cache. llama.cpp itself recommends it in its logs.
  • --no-mmproj: does not load the model's image encoder, which needed 861 MB of VRAM the card no longer had.
  • -np 1: a single request processed at a time (see step 5).
  • -ngl 99 --n-cpu-moe 36: the whole model on the GPU, except the experts of 36 layers, sent back to RAM.
  • -b 2048 -ub 2048: reads the prompt in batches of 2,048 tokens. Experts stored in RAM must be transferred to the GPU for each batch, and the NAS's PCIe 4.0 x4 slot tops out at about 8 GB/s: bigger batches mean fewer transfers. With this setting, prompt reading went from 132 to 343 tokens/s.
  • -t 6: 6 CPU threads (see step 3).
  • -c 32768 --jinja: a 32K-token context, and the model's own chat format.
docker compose up -d
docker logs -f llama-server

The server is ready when the logs show listening on http://0.0.0.0:8080.

3 Find the right settings with llama-bench

The i5-1235U has 2 performance cores and 8 efficiency cores: the right number of threads cannot be guessed. llama.cpp provides a benchmark tool, included in the full-cuda image, which tests every combination at once. First stop llama-server to free the VRAM:

docker compose stop
docker run --rm --gpus all \
  -v /volume1/docker/llama-cpp/models:/root/.cache/huggingface \
  ghcr.io/ggml-org/llama.cpp:full-cuda --bench \
  -m /root/.cache/huggingface/hub/models--unsloth--Qwen3.6-35B-A3B-GGUF/snapshots/<hash>/Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf \
  -ngl 99 -ncmoe 36,38 -t 4,6,8,10 -p 512 -n 128

Results on my NAS (pp512: reading a 512-token prompt; tg128: generating 128 tokens):

n_cpu_moe  threads  pp512 (tok/s)  tg128 (tok/s)
       36        4          202.8           13.7
       36        6          201.3           15.8
       36        8          197.4           15.8
       36       10          198.6           14.7
       38        4          193.3           13.2
       38        6          191.1           15.2
       38        8          193.5           15.1
       38       10          192.4           14.1

Beyond 8 threads, the efficiency cores slow everything down. 6 threads give the same speed as 8 while loading the CPU less. Going from 38 to 36 layers of experts in RAM only gains 0.6 token/s, and going lower overflows the VRAM. The best setting is therefore --n-cpu-moe 36 -t 6.

4 Pitfalls I ran into
  • Out of VRAM at startup (cudaMalloc failed: out of memory): with --n-cpu-moe 32, the weights alone already took 5.85 GB. You need to leave room for the context cache and the compute buffers, which grow with -ub 2048.
  • Automatic fitting disabled: the line failed to fit params ... n_gpu_layers already set by user shows that llama.cpp can split the model on its own, but only if -ngl is not set. In my case, the values found with the benchmark gave better results than this automatic fitting.
  • The image encoder: Qwen3.6 is multimodal, and -hf also loads its vision part, causing another VRAM shortage. Fix: --no-mmproj, or --no-mmproj-offload to keep it on the CPU.
  • The wrong cache folder: the model is downloaded into /root/.cache/huggingface. With a volume mounted elsewhere, the 21 GB stay inside the container and are downloaded again every time it is recreated. To recover an already downloaded model: docker cp llama-server:/root/.cache/huggingface/. ./models/.
  • Only one engine at a time on the GPU: once llama-server is loaded, the VRAM is 98% full and Ollama can no longer load a model (memory error). You have to stop one to use the other.
5 Connect llama-server to Open WebUI and lighten requests

llama-server exposes an OpenAI-compatible API. In Open WebUI: Admin Panel → Settings → Connections → OpenAI API, add the URL http://<ip_nas>:8080/v1 with any key (for example none). The model then shows up in the list, next to the Ollama ones.

During the first tests, a one-line question still sent more than 7,000 tokens of prompt: Open WebUI's built-in tools (notes, user input, file display…) add their descriptions to every request, and the model used them for no reason, with failed calls. So I created a custom model dedicated to chatting (Workspace → Models):

  • Built-in tools: disabled;
  • Vision: disabled, since the server runs without the image encoder;
  • Code interpreter: disabled, as it only runs Python and adds instructions to the prompt;
  • File in context: enabled, so the model reads uploaded files in full.

Result: the prompt for a simple question dropped from more than 7,000 tokens to about thirty.

Second lever, thinking mode. For "the Fibonacci sequence in Rust with a plot", the model generated 5,555 tokens, i.e. 7 minutes, mostly spent thinking. In Model controls, I added a "Thinking" menu with two options, Off by default:

Option   Parameter               Value
On       chat_template_kwargs    {"enable_thinking": true}
Off      chat_template_kwargs    {"enable_thinking": false}

For a model served by Ollama, the parameter is called think (values true / false). Without thinking, an equivalent answer takes 1,300 to 1,800 tokens, i.e. about 2 minutes.

Finally, why -np 1: with 4 slots, the server processed the current answer in parallel with Open WebUI's background requests (title and tag generation), which shared the RAM bandwidth. Generation dropped to 9.3 tokens/s; with a single slot, it goes back up to 15.4.

6 Verdict: Ollama or llama.cpp? 
                               Ollama (start)     llama.cpp (final)
Generation                     14 tok/s           15.4 tok/s
Reading a long prompt          158 tok/s          343 tok/s
Prompt for a simple question   ~2,000 tokens      ~30 tokens
Thinking                       always on          optional

Applying the same settings on the Ollama side (tools disabled, think set to false, 32K context, 6 threads), I get 14.5 tokens/s: on a short question, most of the gain therefore comes from the Open WebUI configuration, not from the engine. llama.cpp's clear advantage is prompt reading twice as fast, which matters as soon as you give it files to read or use an agent. Ollama remains simpler and lets you switch models in one click.

One last useful point, the prompt cache: on the second message of a conversation, llama-server reused 1,848 of 1,891 tokens and only read the new ones. The answer started in 1.3 seconds.

Tuto 6 — An AI agent on the NAS, driven from Telegram (OpenClaw)

OpenClaw is a self-hosted AI agent. Unlike Open WebUI, which only chats, it can act: read and write files, run commands, schedule tasks. You talk to it from a messaging app (Telegram, Discord, Slack, WhatsApp). It is a bit like a Claude Code you drive from your phone, without having to connect to the VPN.

OpenClaw is not an engine: it is a harness, the program that wraps the model and runs it in a loop with tools. It needs an LLM, here the Qwen3.6 35B-A3B from tutorial 5, served by Ollama.

On the other hand, messages go through Telegram's servers, and conversations with a bot are not end-to-end encrypted: I never send anything sensitive there. To reach Open WebUI remotely, I keep using the VPN from tutorial 1.

Security. An agent that reads messages and can run commands on the NAS is an ideal target for prompt injection: a booby-trapped file or message can make it do something other than what was asked. I only give it access to two dedicated folders, the bot only answers my account, and I never install a third-party extension (skill) without reading it first.
1 Prepare Ollama for an agent

First stop llama-server (tutorial 5) to free the VRAM:

docker stop llama-server

An agent sends very large prompts: instructions, tool descriptions, history. Ollama uses a short context by default, and silently truncates the prompt when it is exceeded. So we create a variant of the model with its own settings:

docker exec -it ollama sh -c 'printf "FROM qwen3.6:35b-a3b-q4_K_M\nPARAMETER num_ctx 32768\nPARAMETER num_thread 6\nPARAMETER temperature 0.6\nPARAMETER presence_penalty 0\n" > /tmp/Modelfile && ollama create qwen3.6-agent -f /tmp/Modelfile'

docker exec ollama ollama show qwen3.6-agent --parameters
  • num_ctx 32768: a 32K-token context;
  • num_thread 6: the best setting found in tutorial 5;
  • temperature 0.6 and presence_penalty 0: the settings Qwen recommends for code. A presence penalty pushes the model to avoid repetition, which gets in the way when it needs to reuse the same variable names.
Why not do this in Open WebUI? Open WebUI's custom models only exist within Open WebUI, which adds their settings to the requests it sends. OpenClaw talks to Ollama directly, so the variant has to exist in Ollama itself.

Then, in the docker-compose.yml from tutorial 2, add two environment variables to the ollama service:

    environment:
      - OLLAMA_HOST=0.0.0.0
      - OLLAMA_ORIGINS=*
      - OLLAMA_KEEP_ALIVE=-1
      - OLLAMA_NUM_PARALLEL=1
  • OLLAMA_KEEP_ALIVE=-1: the model stays loaded in memory. Otherwise, every task starts with a minute of loading;
  • OLLAMA_NUM_PARALLEL=1: one request at a time, the equivalent of -np 1 in llama.cpp.
cd /volume1/docker/ai-stack
docker compose up -d
docker exec ollama env | grep OLLAMA
curl http://<ip_nas>:11434/api/tags

OpenClaw runs in its own container: for it, localhost means that container, not the NAS. You therefore have to use the NAS's local IP address, and check that qwen3.6-agent appears in the curl response.

5 Errors I ran into

"No API key found for provider "openai"": the Ollama provider had been added, but the agent was still using OpenAI by default.

"Request timed out before a response was generated", always after one minute. Ollama's logs explain why: OpenClaw's system prompt, with its tool descriptions, is about 13,000 tokens. At about 150 tokens/s, the model needs nearly 85 seconds to read it before writing the first word.

The timeout suggested by the error message (agents.defaults.timeoutSeconds) is not enough: the version installed by UGOS (2026.3.31) has a second timeout, 60 seconds by default, for the wait before the first token. Both need to be raised:

Tip: while testing, send a single message and wait. With one request at a time, each new message joins the queue. To avoid the minute of loading, you can also preload the model:
curl http://<ip_nas>:11434/api/generate -d '{"model":"qwen3.6-agent","keep_alive":-1}'

"Exec approval is required, but no interactive approval client is currently available", followed by "I can't find the file". I had asked it to summarize a file dropped in the shared folder, but the agent did not know where that folder was mounted: it tried a find over the whole of /root. Shell commands require approval, and since no approval method was configured, the request timed out and the command was denied. This is the expected behaviour: this safeguard stops the agent from searching through the system.

The fix is to give it the exact path. To see where each folder is mounted in the container:

docker inspect openclaw-gateway-1 --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
/volume1/docker/openclaw/workspace -> /root/.openclaw/workspace
/volume1/docker/openclaw/share -> /volume1/docker/openclaw/share

Then tell the agent, once and for all:

The shared folder is /volume1/docker/openclaw/share. Write this path down in your memory files.

With the exact path, it reads files with its file-reading tool, without going through the shell, so no approval is needed. To still allow some shell commands, with a confirmation each time, see step 7 (and the approvals documentation).

6 First contact: the agent's identity and rules

On the first message, OpenClaw starts an onboarding step: it asks for its name, nature, style and an emoji, then saves everything in Markdown files in its workspace (IDENTITY.md, USER.md, SOUL.md…). These files act as its memory: it reads them again at every session. I answered in a single message to limit back-and-forth:

Call yourself Atlas, technical assistant for my NAS, IT/AI/LLM/Tech specialist, direct and concise style, emoji 🛰️

Then I set its behaviour rules, which it saved in SOUL.md:

- Short, direct answers, in French.
- No Markdown tables, Telegram does not display them: use lists.
- Always ask me for confirmation before deleting a file
  or running a command that modifies the system.
- Only work in your workspace and in the shared folder.

Two remarks:

  • The agent announced "Done" even though one of its edits to SOUL.md had failed. Models of this size often claim to have succeeded at a failed action: you have to check the file yourself (here, everything was there).
  • These rules help, but they are not real protection: the agent can rewrite its own files. If you ever give it access to external content (web pages, emails), you can make the file read-only: chmod 444 <path>/openclaw/workspace/SOUL.md.

At the end of onboarding, it offers to delete BOOTSTRAP.md, which is no longer needed. A good sign: it asked for confirmation before doing so.

cp /volume1/@appstore/com.ugreen.docker.openclaw/config/openclaw.json \
   /volume1/@appstore/com.ugreen.docker.openclaw/config/openclaw.json.bak

Then enable approvals, replacing YOUR_ID with your Telegram ID:

docker exec -it openclaw-gateway-1 openclaw config set channels.telegram.execApprovals.enabled true
docker exec -it openclaw-gateway-1 openclaw config set channels.telegram.execApprovals.approvers '[YOUR_ID]'
docker exec -it openclaw-gateway-1 openclaw config set channels.telegram.capabilities.inlineButtons dm

docker exec -it openclaw-gateway-1 openclaw config get channels.telegram
docker restart openclaw-gateway-1
  • execApprovals.approvers: the list of approvers. In the output of config get, it must appear as a list containing a number, not as quoted text;
  • capabilities.inlineButtons dm: allows buttons in private messages, needed to approve with a single tap.

To test it, I ask Atlas: "Run ls -la /volume1/docker/openclaw/share". The bot replies with an "Approval required" message showing the command, the folder it will run in and the expiry time (30 minutes), followed by three buttons:

  • Allow Once: allows this command a single time. This is the default choice;
  • Allow Always: adds the command to a permanent allowlist, so the agent can run it again without asking. I only use it for read-only commands I see often, never for a command that deletes, moves or downloads something;
  • Deny: refuses the command.

The same choices exist as commands to type (/approve <id> allow-once, allow-always or deny). Simply replying "yes" in the conversation does not count as an approval.

Good to know: the "Host: gateway" line means commands run inside OpenClaw's container, as root, not directly on the NAS system. They can only reach the folders mounted in that container. This is an extra layer of protection, but not an absolute guarantee: the real safeguard is still to read every command before approving it, and to deny anything that goes beyond workspace and share.
8 Cut the agent off from the Internet

The model itself never has Internet access: Ollama only produces text. What can reach the Internet is OpenClaw, through its tools. The logs show it from the very first exchanges: web_search: no provider configured ... falling back to keyless provider "duckduckgo". Web search is enabled by default, without a key, through DuckDuckGo. And a web page is the most likely source of prompt injection.

Three doors lead to the Internet:

  • web_search and web_fetch (group group:web): searching and reading web pages;
  • browser (group group:ui): a browser driven by the agent;
  • shell commands such as curl or wget, already subject to approval since step 7.

The container's network itself cannot be cut: OpenClaw needs it to talk to Telegram. So the tools are denied instead, after backing up the configuration:

docker exec -it openclaw-gateway-1 openclaw config set tools.deny '["group:web","browser"]'
docker exec -it openclaw-gateway-1 openclaw config set tools.web.search.enabled false
docker exec -it openclaw-gateway-1 openclaw config set tools.web.fetch.enabled false
docker restart openclaw-gateway-1

docker exec -it openclaw-gateway-1 openclaw config get tools

A denial (tools.deny) always wins over any permission. I check with config get after the restart, because Ugreen's manager rewrites part of the configuration on every start (Syncing configuration from environment variables... in the logs).

To test it, I ask Atlas: "Search the web for the latest version of Ollama". It no longer has a web tool… and immediately tries to get around it with a shell command:

curl -s https://api.github.com/repos/ollama/ollama/releases/latest | grep -o '"tag_name": *"[^"]*"' | head -1

The approval from step 7 stops it: I refuse with Deny, and never use Allow Always for curl or wget. To make it stop trying, I added this rule directly to SOUL.md:

- You have no Internet access. Never use curl, wget or any other way
  to contact an external site. If something requires the Internet, tell me.

In the end, three layers of protection: web tools disabled, an instruction that discourages the agent from trying (which it may not follow), and the approval of every shell command, which remains the real barrier. Denying a tool is not enough as long as the shell is available. Bonus: each removed tool takes its description out of the system prompt, which makes answers slightly faster.

Watch the logs: on startup, the container logs print a token in clear text (--token …). Mask it before sharing logs. If it is the gateway token chosen at installation, UGOS only lets you change it by resetting the app: you then have to redo the configuration from this tutorial (the workspace and share folders, and therefore the agent's memory, are kept).
9 Performance and ways to improve it

On this setup, the first answer arrives in a little over a minute, and a task with several tool calls (writing files, then answering) takes about 4 minutes. This is much slower than Open WebUI, for two reasons: the prompt goes from about thirty tokens to about 13,000, and each tool call runs the model again. Usage is therefore rather asynchronous: you send a request from Telegram and come back for the result later.

Ways to speed it up:

  1. Connect OpenClaw to llama-server (tutorial 5) instead of Ollama: prompt reading is twice as fast there, and that is exactly what limits an agent.
  2. Check that the prompt cache works from one turn to the next (docker logs ollama | grep cached). If the whole prompt is read again at every turn, that is what costs the most.
  3. Shrink the system prompt further by disabling other unneeded tools (web tools are already disabled since step 8).
  4. Disable thinking, at the cost of less reliable actions.
